# Поручение Claude на перенос платформы

Возьми разработанное готовое решение из GitHub и выполни работу в два этапа: **сначала разверни его целиком** на `root@147.45.41.148` для `https://synergyhub.top`, **затем исправь фронтенд**, сохранив пользовательские сценарии, алгоритмы, API, структуру БД и существующие данные.

## Откуда получить файлы

- **Код, миграции, Docker, документация:** https://github.com/dmonaidev/meteora-pilot-tournament
- **Полная база и готовая конфигурация:** https://github.com/dmonaidev/meteora-pilot-tournament-transfer — приватная репозитория того же владельца. Нужен доступ через подключённый GitHub владельца.

В приватной репозитории:

| Файл | Назначение |
| --- | --- |
| README.md | Порядок скачивания и запуска |
| data/application-data.json | Полная база: участники, реестр, кошельки, UID, статусы, результаты, настройки и версии правил |
| config/deploy.env | Готовая конфигурация production: действующий BOT_TOKEN, административные Telegram ID, новые секреты и пароль новой БД |
| config/local-source.env | Исходная локальная конфигурация для сверки; не использовать её на сервере без адаптации |

| server-access.json | Сервер, домен и предполагаемый путь SSH-ключа |

Скачай файлы через авторизованный GitHub или клонируй обе репозитории. Настройки турнира, административные ID и токен бота уже в приватном комплекте. Если он недоступен, попроси подключить приватную репозиторию к GitHub-интеграции Claude.

## Первый этап развернуть готовое решение

1. Прочитай `AGENTS.md`, `Agent.md`, `docs/delivery/design-preservation.md`, `docs/product/screens-and-access.md`, `docs/product/access-and-cabinet.md`, `docs/delivery/server-transfer.md` и README приватной репозитории.
2. Проверь SSH-доступ и серверную инфраструктуру. SSH-ключ отсутствует на исходной машине и не включён. Предложенный путь `~/.ssh/meteora_deploy_r3`; проверь доступный ключ или запроси его у владельца. Сохрани неизвестные соседние сервисы.
3. Собери существующий проект через `Dockerfile` и `deploy/compose.yml`. Скопируй приватный `config/deploy.env` в `deploy/.env` с правами 600. Не публикуй его содержимое и не добавляй в публичный Git.
4. Запусти новую PostgreSQL и восстанови **полный приватный** `data/application-data.json` через `scripts/handoff.mjs restore FILE --fresh-database`. Не запускай демозаполнение и не импортируй сначала публичный JSON.
5. Запусти приложение, настрой virtual host, HTTPS и автозапуск. Базу не публикуй в интернет. Приложение запускается штатным пользователем образа.
6. Перед запуском серверного бота убедись, что прежний локальный polling остановлен. Если доступа к компьютеру владельца нет, дай один конкретный шаг для остановки. На токен допускается один polling-процесс. Новый бот создавать не нужно.
7. Проверь внешний сайт, вход администратора и участника, правила, статусы, лидерборд, UTC/24 часа, сессию 30 минут и сохранение после рестарта. Зафиксируй исходное состояние работающего решения и данные перед исправлением фронтенда. Реальные данные и даты ради проверки не меняй.

## Второй этап исправить фронтенд

После успешного развёртывания исправь ошибки отображения и вёрстки существующего фронтенда: загрузку ресурсов, читаемость, адаптивность, перекрытия/переполнение и визуальную согласованность. Опирайся на существующие `web/src/`, описание экранов и снимки в приватной репозитории. Сохрани разработанное приложение; не создавай замену с нуля.

Сохрани последовательность действий, формы, поля и условия их появления, роли, проверки, сценарии регистрации/входа, номинаций, Telegram-бота и модерации. Не меняй сервер, бот, алгоритмы, API, миграции, структуру БД, статусы, настройки и загруженные записи ради исправления фронтенда. Не добавляй новую бизнес-логику.

Фронтенд менять только с явного разрешения пользователя и в пределах согласованной правки. Изменение сценария/алгоритма/контракта/базы требует отдельного явного разрешения пользователя. Если конкретная неисправность требует такого изменения, опиши её и получи разрешение до реализации.

После правок собери UI штатно, проверь 1440px и 390px, прогони существующие проверки на изолированной БД и сравни исходное и итоговое состояние. Рабочие профили и настройки должны сохраниться. Передай владельцу URL, SHA, список исправлений фронтенда, результаты проверки сценариев и сохранности базы, команды эксплуатации без секретов.

## Обязательное согласование изменений

**Изменения пользовательских сценариев, алгоритмов, API, структуры БД и существующих данных допускаются только после отдельного явного разрешения пользователя — владельца проекта.** Разрешение исправить фронтенд не является разрешением менять эти сценарии. При необходимости предложи конкретную правку и дождись разрешения до её реализации.

Используй существующие компоненты `web/src/` и CSS как исходное готовое решение. Не восстанавливай продукт из исторической модели 0.2.1. Карта экранов и границы исправления фронтенда — в `docs/delivery/design-preservation.md` и `docs/product/screens-and-access.md`.

## Уточнение владельца: разрешение и риск изменений

Запрещено самовольно менять алгоритмы, пользовательские сценарии, маппинг переменных между UI/API/ботом/БД, API-контракты, структуру БД и существующие записи. Сохранять имена полей, соответствия, типы, enum/null, единицы измерения и ведущие нули UID. Фронтенд менять только с явного разрешения пользователя в рамках согласованной правки. Развёртывание само по себе не разрешает менять фронтенд; разрешение менять фронтенд не разрешает менять защищённые части.

Если запрошенная пользователем правка может нарушить работу приложения, сценарии, алгоритмы, маппинг переменных, API или данные, до реализации предупредить пользователя: описать конкретные последствия и затронутые части, предложить безопасный вариант, запросить отдельное явное разрешение и дождаться ответа. Сам факт запроса правки и общее разрешение менять фронтенд не заменяют согласия на эти последствия.
