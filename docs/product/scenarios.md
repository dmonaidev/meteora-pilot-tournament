# Сценарии криптотурнира

Версия 0.2.1. Цепочка продукта: регистрация → проверка допуска → ввод и проверка данных → загрузка скоринга администратором → лидерборд. Форматы указаны в [API](../contracts/api.md); порядок записи — в [алгоритмах](../architecture/algorithms.md).

## SC-01 Регистрация

Роль: посетитель. Предусловие: display_name после trim имеет 3–20 символов.

1. Сайт отправляет POST /api/v1/auth/register с display_name.
2. Сервер создаёт pending_sessions: REGISTRATION, reg_ token, display_name, tg_id=null, is_used=false, created_at=UTC now.
3. Сервер возвращает token и bot_link. Сайт показывает кнопку подтверждения и опрашивает auth/session/{token} раз в 3 секунды.
4. Пользователь открывает бота и нажимает Старт. Бот отправляет token, message.from.id и username на bot/verify.
5. Сервер ищет users по tg_id. Если профиля нет, проверяет initial_users и создаёт users с APPROVED_AUTO либо PENDING_VALIDATION.
6. В той же транзакции сервер фиксирует tg_id и is_used=true в pending_sessions.
7. Бот сообщает результат. Polling получает JWT, завершает ожидание и открывает ЛК.
8. В форме заполнения данных регистрации/ЛК пользователь видит wallet_address, withdrawal_tx_hash и существующий блок выбора наград/UID биржи. Адрес и хэш отправляются вместе по SC-05; reward_type и exchange_uid — по SC-07.

Итог: один users и подтверждённая pending_session. Кошелёк, награды и scoring автоматически не создаются.

Повторная регистрация того же tg_id использует существующий профиль, сохраняет имя и ручной статус. При неверном имени запись не создаётся. При истёкшем token подтверждение запрещено. Сайт после успеха или истечения прекращает polling.

## SC-02 Повторный вход

Роль: пользователь с существующим users. Сайт создаёт AUTHORIZATION через auth/login, без display_name. Бот подтверждает auth_ token и tg_id. Сервер находит профиль, обновляет username, фиксирует pending_session и возвращает результат входа через polling.

PENDING_VALIDATION и REJECTED тоже могут войти в ЛК. Их registration_status не меняется. Если users не найден, USER_NOT_REGISTERED; профиль без имени не создаётся.

## SC-03 Повтор подтверждения и истечение

С тем же token и tg_id бот получает success и текущий registration_status без второго users. Другой tg_id после подтверждения → SESSION_ALREADY_BOUND. При now >= created_at + 15 минут → SESSION_EXPIRED независимо от is_used.

Параллельные регистрации одного tg_id дают один users за счёт UNIQUE и транзакции. Повторный polling подтверждённой неистёкшей сессии не создаёт новый профиль. Весь процесс завершается на сервере до сообщения об успехе.

## SC-04 Допуск администратором

Роль: администратор. Отправить users/moderate: tg_id, action APPROVE/REJECT, admin_notes.

APPROVE устанавливает APPROVED_MANUAL, REJECT — REJECTED. Комментарий обязателен при ручном изменении. Wallet, reward и score при этом не меняются. При следующем запросе leaderboard применяет новый статус. Повтор той же команды с тем же комментарием сохраняет тот же результат.

Отсутствующий пользователь → USER_NOT_FOUND; нет admin-права → FORBIDDEN; пустой комментарий → VALIDATION_ERROR.

## SC-05 Ввод и повторная отправка кошелька

Роль: любой авторизованный пользователь. Ввод данных разрешён при любом registration_status. Поля wallet_address и withdrawal_tx_hash обязательны и отправляются вместе. Signature не требуется.

Первый адрес создаёт wallets с UNDER_REVIEW и rejection_reason=null. До TOURNAMENT_START_AT изменённый адрес обновляет ту же запись, получает новый поданный хэш, UNDER_REVIEW и очищенную причину. Для того же адреса новый хэш тоже сбрасывает проверку. Идентичная пара адрес/хэш в UNDER_REVIEW/VALID сохраняет статус; после INVALID повтор этой пары устанавливает UNDER_REVIEW и очищает причину.

При now >= TOURNAMENT_START_AT смена существующего адреса запрещена независимо от статусов и наличия score: 409 WALLET_CHANGE_LOCKED без изменений. Запрет применяется и к INVALID/UNDER_REVIEW адресу. Первая подача без wallet разрешена этим правилом; допуск определяется отдельно. Тот же адрес можно подать повторно или исправить хэш.

Система проверяет формат адреса и обязательный текстовый хэш, не проверяет владение криптографически и не подтверждает транзакцию автоматически. Неверный формат или пустой хэш не меняют запись.

Смена адреса до старта, смена только хэша и повторная подача не изменяют готовые значения scoring: они привязаны к user_id и управляются администратором. Приложение не удаляет и не пересчитывает их автоматически. Закрытое исключение администратора описано в ALG-11 и не предлагается участнику как функция.

## SC-06 Валидация кошелька

Роль: администратор. Передать user_id, проверенные wallet_address и withdrawal_tx_hash, action VALID/INVALID и rejection_reason при отказе.

Администратор вручную проверяет адрес и указанный хэш вывода с биржи на этот кошелёк. Сервер под блокировкой проверяет совпадение обоих значений с текущими. Иначе WALLET_CHANGED, админ читает актуальные данные. VALID очищает rejection_reason; INVALID требует непустую причину.

Пользователь видит статус и причину. VALID открывает блок scoring; если загрузки не было, показывается отсутствие данных. Для leaderboard дополнительно нужна одобренная регистрация. Модерация работает и после старта, но не заменяет адрес и не обходит запрет смены.

## SC-07 Выбор наград и UID

Роль: любой авторизованный пользователь.

- RESPECT: exchange_uid=null, uid_status=NOT_REQUIRED.
- PARTNER_GIFTS: обязательный непустой exchange_uid, uid_status=UNDER_REVIEW.
- Смена UID или переход на PARTNER_GIFTS устанавливает UNDER_REVIEW; переход на RESPECT устанавливает NOT_REQUIRED.
- Повтор тех же PARTNER_GIFTS и UID сохраняет прежний uid_status.
- RESPECT принимает только отсутствующий exchange_uid или null. Любое другое значение, включая пустую строку, отклоняется с 422.

При INVALID UID пользователь видит статус и может изменить значение. Отдельное поле причины отказа UID не добавляется: его нет в исходной модели.

## SC-08 Проверка UID

Роль: администратор. Передать user_id, проверенный exchange_uid и action VALID/INVALID.

Сервер проверяет существование partner_rewards, тип PARTNER_GIFTS и совпадение текущего UID с проверенным. Изменившийся UID → UID_CHANGED. Для RESPECT → UID_NOT_REQUIRED.

VALID даёт Special Partner Gift; UNDER_REVIEW/INVALID — RespectGift. Проверка UID не меняет допуск и кошелёк.

## SC-09 Импорт initial_users

Роль: администратор. Исходный CSV содержит Telegram ID и справочные поля списка. Админка передаёт серверу rows с исходными названиями колонок.

Проверить весь набор, нормализовать username и null, проверить обязательные поля и дубли. При отсутствии ошибок upsert initial_users по tg_id. Строки вне загрузки не удаляются, существующие users не меняются.

Повтор одинакового набора не создаёт дубликаты. Ошибка любой строки отменяет всю загрузку. Ответ содержит inserted и updated; updated означает строку, существовавшую после получения блокировки импорта и до записи, даже при тех же значениях (ALG-07).

## SC-10 Загрузка скоринга администратором

Роль: администратор. Для каждой строки он подготавливает tg_id и готовый pnl. initial_capital, current_capital, in_positions_amount и roi_percentage необязательны и справочны.

1. Админка отправляет admin/scoring/import с rows.
2. Сервер проверяет все строки и сопоставляет tg_id с users.id.
3. pnl обязателен, может быть отрицательным или нулевым; остальные метрики могут отсутствовать/null.
4. В одной транзакции вставляет или обновляет tournament_scoring по user_id. Отсутствующие справочные поля заменяются null, а не прежними значениями.
5. Результаты пользователей вне запроса не меняются.
6. ЛК и leaderboard при следующем чтении получают загруженные данные.

Загрузка возможна до завершения допуска и не меняет статусы регистрации/кошелька/UID. Неизвестный tg_id, дубликат строки, неверный decimal или ROI отклоняют весь набор до записи.

Сайт не вычисляет PNL или ROI, не получает баланс/котировки и не прибавляет позиции к капиталу. Повтор той же загрузки сохраняет те же значения без дублей. Повтор с pnl и без прежнего ROI очищает ROI.

## SC-11 Личный кабинет

GET user/profile возвращает профиль, вычисляемый wallet_address_locked и wallet/rewards/scoring как объект либо null.

PENDING_VALIDATION показывает ожидание модерации. REJECTED показывает отказ в допуске. Поля кошелька и наград доступны в обоих случаях. UNDER_REVIEW — проверка, INVALID wallet — причина и повторный ввод, VALID — блок scoring.

Без VALID кошелька scoring в ответе профиля скрывается как null даже при существующей записи. При VALID и отсутствии записи показывается «Данные ещё не загружены». PNL отображается как основной результат, ROI — только справочно при наличии. Регистрационный статус этим не меняется.

Адрес и withdrawal_tx_hash показываются участнику. wallet_address_locked=true делает существующий адрес недоступным для изменения; хэш можно исправить с повторной проверкой. Интерфейс не рекламирует административное исключение.

## SC-12 Публичный лидерборд

Сервер выбирает только APPROVED_AUTO/APPROVED_MANUAL с VALID кошельком. Присоединяет scoring и partner_rewards без исключения пользователя при отсутствии этих записей.

Формирует reward_tag. Нет scoring → pnl и четыре справочные метрики null, а не 0. Пустой результат → []. Сортировка pnl DESC NULLS LAST, затем user_id ASC при равенстве. ROI и капитал не влияют на порядок.

После REJECTED или INVALID wallet участник исчезает из списка; загруженный score остаётся в БД. После восстановления обоих условий допуска отображается сохранённый результат того же user_id, включая разрешённую смену адреса до старта или закрытое исключение ALG-11.

## Переходы состояний

| Сущность | Действие | Из состояния | В состояние |
| --- | --- | --- | --- |
| users | Новая регистрация, ID есть в списке | Нет записи | APPROVED_AUTO |
| users | Новая регистрация, ID нет в списке | Нет записи | PENDING_VALIDATION |
| users | Ручное APPROVE | Любое существующее | APPROVED_MANUAL |
| users | Ручное REJECT | Любое существующее | REJECTED |
| users | Повторный вход | Любое | То же |
| wallets | Первая подача; новый адрес до старта; новый хэш | Нет записи / прежние данные | UNDER_REVIEW |
| wallets | Повтор той же пары адрес/хэш | VALID / UNDER_REVIEW | То же |
| wallets | Попытка смены адреса после старта | Любое существующее | Без изменений, WALLET_CHANGE_LOCKED |
| wallets | Повтор той же пары после отказа | INVALID | UNDER_REVIEW |
| wallets | Ручная проверка | Любое | VALID / INVALID |
| partner_rewards | RESPECT | Любое / нет записи | NOT_REQUIRED |
| partner_rewards | Новый PARTNER_GIFTS / UID | Любое / нет записи | UNDER_REVIEW |
| partner_rewards | Идентичные данные | Любое | То же |
| partner_rewards | Ручная проверка PARTNER_GIFTS | Любое состояние проверки | VALID / INVALID |
| pending_sessions | Успешный bot/verify | is_used=false | is_used=true |

Истечение pending_session вычисляется из created_at; новый enum для него не вводится.
