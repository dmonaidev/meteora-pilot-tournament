# Техническая спецификация доступа и личного кабинета

Версия 1.3, 08.10.2026. Спецификация локального продукта с дополнениями [расписания и публичных показателей](../decisions/schedule-stats-v0.8.md) и [квалификации Special Gift](../decisions/partner-qualification-v1.2.md). Для этих сценариев имеет приоритет над историческими описаниями экранов. Детали продления и хранения сессий: [контракт 0.7](../decisions/session-v0.7.md). Структура данных профиля: [API](../contracts/api.md) с дополнениями 0.3–1.3 и [контрактом правил](../decisions/rules-v1.0.md).

## 1. Роли и права

Авторизованный пункт «Личный кабинет» открывает профиль пользователя, его данные/статусы и ранее утверждённые общие показатели. Он заменяет неоднозначное название «Главная». Выбор разделов админки немедленно переключает плитку, заголовок и нижнюю область; загрузка/ошибка относится только к текущему разделу, старые ответы не возвращают прежнюю таблицу или редактор. Даты на всех экранах и в таблицах показываются в UTC.

Ввод расписания всегда в24часовом формате ЧЧ:ММ, с примечанием «24 часа · UTC» у каждого поля. Кнопка часов открывает компактный выбор00–23/00–59; AM/PM не используется независимо от языка браузера. Сохранённые ненулевые секунды видны и сохраняются; неизменённые ISO-значения не теряют точность.

Название турнира задаётся отдельной формой в Настройках турнира, первоначально PILOT TOURNAMENT. Бренд гостевой страницы/меню и заголовок лидерборда читают одно серверное tournament_name; после сохранения обновляются без повторного входа. Расписание и рефссылка не меняются; подробности — [контракт1.3](../decisions/tournament-name-v1.3.md).

| Роль | Способ определения | Доступ |
| --- | --- | --- |
| Гость | Нет активной серверной сессии | Публичный лидерборд, агрегированные показатели и расписание, вход, правила и архив; новая регистрация в открытом окне при опубликованных правилах |
| Участник | Telegram подтверждён кодом, серверная сессия активна | Свой ЛК, сохранение своего кошелька/UID, лидерборд |
| Администратор | Подтверждённый tg_id включён в ADMIN_TG_IDS | Админка: участники, реестр допуска, кошельки, UID и награды, результаты, сессии входа, настройки турнира, правила и версии; также свой ЛК и лидерборд |

Роль не передаётся пользователем. Вход в ЛК, допуск к турниру, проверка кошелька и проверка UID — разные состояния.

Под приветствием показывается краткая строка заявки: Special Gift ожидает проверки партнёра / подтверждён партнёром; только Respect Gift ожидает проверки / допуск подтверждён. Номинация определяется сохранённым UID, а подтверждение — сохранёнными ручными статусами. Отклонение показывается отдельно, без ложного ожидания/успеха. Для Respect Gift подтверждение требует одобренного допуска и VALID кошелька; для строки подтверждения партнёра требуется UID VALID, общий допуск остаётся отдельным.

Над UID — приглашение к Special Gift, ссылка квалификации и раскрываемая минипанель. Под проверкой данных справа — семь шагов дорожной карты по контракту1.2. Регистрацию на бирже по ссылке, депозит от100 USDT и объёмы спот-обмена проверяет администратор вручную; шаги не подтверждаются автоматически от ввода. SOL выводится на **Ваш турнирный кошелёк**. Проверка UID теперь подтверждает совокупные условия партнёра, её API сохраняется. Реферальный URL администратор задаёт в Настройках турнира отдельной формой, все ссылки ЛК/баннера читают один источник. Пока ссылка не опубликована, фиктивного перехода нет.

## 2. Регистрация и повторный вход

### Правила и версия согласия

«Правила» доступны гостю в шапке и в меню лидерборда/ЛК. Окно показывает действующий plain text и выбор опубликованных архивных редакций. Закрытие возвращает в регистрацию без потери имени, Telegram, галочки или ожидающего кода.

При новой регистрации checkbox «Я ознакомился и согласен с правилами турнира» изначально выключен. Сервер принимает только true и ID текущей ACTIVE версии. В pending_sessions записывается ID/серверное время; при создании users оба Telegram-пути копируют эти данные. Публикация новой редакции после начала регистрации сохраняет действительность принятой прежней версии до истечения pending. Явное удаление принятого архива до завершения требует нового согласия.

Без опубликованных правил новая регистрация недоступна с пояснением; существующий вход работает. Правила не меняют срок сессии, выдачу кода, допуск и ручную проверку кошелька/UID. У старых аккаунтов согласие остаётся null.

Админка → «Правила»: создать или загрузить .txt/.md в черновик, сохранить, опубликовать. Новая публикация архивирует прежнюю. Опубликованный и архивный текст неизменяемы; изменения оформляются новым черновиком, можно скопировать старую версию. Архив доступен до явного подтверждённого удаления администратором; автоматической очистки нет. Приложенный draft-2026-10-01 сохранён только как черновик.

1. Регистрация: display_name от 3 до 20 символов после trim и Telegram username либо числовой ID. Новая регистрация требует обязательной незаполненной по умолчанию галочки согласия с опубликованной редакцией. Повторный вход: только username либо ID.
2. Username принимается с одним ведущим @ и без него, обрезаются внешние пробелы. Сравнение без учёта регистра, в БД хранится без @. ID — положительный safe integer; ведущий @ к ID не добавляется. Проверка входа не полагается на совпадение display_name.
3. POST /auth/register либо /auth/login создаёт website pending session на 15 минут. Сайт показывает поле шестизначного кода и явный адрес бота @lptournamentsupport_bot.
4. POST /auth/code/request пытается автоматически отправить код ранее подтверждённому пользователю по его сохранённому tg_id. Неизвестный пользователь открывает бота на телефоне и нажимает Start / отправляет /start. Перенос длинного токена между устройствами не нужен.
5. Код действует 5 минут, одноразовый, максимум 5 неправильных попыток. Новый код тому же Telegram ID выдаётся не чаще раза в 90 секунд независимо от @, регистра, вкладки, новой pending session или способа запроса (сайт/бот). Кнопка повторной отправки показывает countdown; refresh не сбрасывает его. Новый допустимый код заменяет предыдущий.
6. POST /auth/code/verify получает token website session, telegram_identifier и code. Сервер проверяет код и личность, связывает сессию и выдаёт JWT. Код не хранится в браузере и не показывается админу.
7. Для нового tg_id создаётся users: APPROVED_AUTO при наличии в initial_users, иначе PENDING_VALIDATION. Повторная регистрация не меняет display_name, ручной статус и admin_notes существующего участника.
8. Администратору открывается админка, обычному участнику — ЛК. USER_NOT_REGISTERED при входе предлагает регистрацию; правильный код не расходуется до создания пользователя с display_name.

Новое создание участника ограничено окном registration_start_at/registration_end_at и окончанием турнира. При null регистрационных дат регистрация открыта до окончания турнира. Границы проверяет сервер при начале регистрации и при подтверждении кода/deep link; REGISTRATION_NOT_OPEN означает ещё не открытое либо закрытое окно. Вход существующих пользователей и действующие сессии продолжают работать. Все четыре даты задаёт администратор; наступившая сохранённая дата не изменяется обычным действием. Времена хранятся, вводятся и показываются только в UTC, независимо от часового пояса браузера. В админке отдельные поля даты/времени с календарём и часами; детали — [контракт1.1](../decisions/utc-admin-v1.1.md).

## 3. Жизненный цикл входа

- Сессия — 30 минут, авторитетный срок хранится в auth_sessions.expires_at. Обычное чтение профиля или polling не продлевает её.
- JWT сохраняется в localStorage для данного origin. Переключение ЛК/лидерборд, refresh и новая вкладка восстанавливают активный вход через GET /auth/access без нового кода. Сервер проверяет подпись, владельца и состояние сессии.
- В последние 5 минут на всех приватных экранах показывается баннер с оставшимся временем и кнопкой «Продолжить через Telegram».
- Нажатие сайта вызывает POST /auth/renew/request. Пользователю бот отправляет кнопку «Подтвердить сессию на сайте» максимум на 5 минут, до исходного deadline. Сам запрос срока не меняет.
- Callback реального владельца Telegram подтверждает POST /bot/session/confirm. Сервер атомарно продлевает эту сессию на 30 минут от подтверждения, аннулирует кнопку; сайт получает новый JWT через GET /auth/access без повторного кода и сохраняет выбранный экран. Другие устройства не авторизуются.
- Если ответ не получен до срока, сессия прекращается. Просроченная кнопка не возвращает доступ; нужен новый вход по коду. Фоновая очистка снимает клавиатуру истёкшего запроса в пределах следующего 15-секундного прохода при доступном Telegram.
- «Выйти» вызывает POST /auth/logout, отзывает серверную сессию и очищает браузерное хранилище/ожидающую авторизацию. Выход и новый JWT синхронизируются между вкладками той же сессии.
- 403 административного API означает отсутствие роли администратора, не выход. Ошибка сети не отменяет ещё действующий доступ. 401 после проверки серверного срока требует входа.

## 4. Данные ЛК и отображение

Источник — GET /api/v1/user/profile. ЛК не получает чужие профили и приватные административные записи.

| Поле/блок | Источник | Отображение и изменение |
| --- | --- | --- |
| Приветствие, имя | display_name | Имя в турнире, readOnly; пользовательская смена имени не реализована |
| Telegram | tg_username | @username либо «Username не задан», readOnly, личность уже подтверждена |
| Допуск | registration_status | APPROVED_AUTO/APPROVED_MANUAL: подтверждён; PENDING_VALIDATION: пока не допущен, обратиться к админу; REJECTED: отклонён, обратиться к админу |
| Контакты | Утверждённые контакты владельца | @LeoCryptus и @D_mOnII, ссылки Telegram при PENDING_VALIDATION/REJECTED |
| Турнир и регистрация | public/tournament: registration_start_at/registration_end_at/start_at/end_at, registration_open/registration_status/started/ended/server_time | Четыре даты либо «не назначена»; открытое, ожидающее или закрытое окно регистрации; ожидающий, начавшийся или завершённый турнир |
| Кошелёк | wallet.wallet_address | Solana Base58, декодируется в 32 байта; nullable wallet означает «Не подан» |
| Проверка кошелька | wallet.validation_status, rejection_reason | UNDER_REVIEW/VALID/INVALID; причина отклонения видна пользователю |
| Фиксация адреса | wallet_address_locked | readOnly существующий адрес после старта; запрет повторно проверяет сервер |
| Участие с UID биржи | rewards.exchange_uid | Checkbox «Указать UID аккаунта на бирже» показывает UID и хэш вывода |
| UID | rewards.exchange_uid, uid_status | Строка до 50 символов, ведущие нули сохраняются; статус проверки отдельный |
| Хэш вывода | wallet.withdrawal_tx_hash | Обязателен только при указанном UID, до 255 символов; без UID равен null |
| Награда | rewards.reward_type, uid_status | Вычисляется сервером, пользователь не выбирает. SpecialPartnerGift только при PARTNER_GIFTS и VALID UID; иначе RespectGift |
| Скор | scoring.pnl | Готовый абсолютный PNL, загруженный администратором; в ЛК показывается при VALID кошельке |

Для внешнего участника PENDING_VALIDATION текст: «Вы пока не допущены к турниру. Обратитесь к администратору для проверки и допуска. Профиль можно заполнить сейчас». Это сообщение также отправляется ему в боте после новой регистрации. Подтверждение Telegram не заменяет административный допуск.

## 5. Сохранение кошелька и UID

[Проверка дубликатов 0.9](../decisions/duplicates-v0.9.md): заполненные корректные кошелёк/UID проверяются через POST /user/profile-check после500мс паузы. Сообщение отображается у поля до сохранения, даже если хэш пока пуст. Чужой дубликат запрещён, собственная сохранённая запись разрешена. Запрос не раскрывает владельца; база защищает от гонки уникальными индексами, конфликт409 атомарно откатывает сохранение пары. Недоступность сети не означает свободное значение.

Результат отображается под каждым полем с иконкой: «Проверяем на дубликаты…», зелёное «Проверено: дубликатов нет», красное сообщение о дубликате или неверном формате. Некорректный непустой адрес также блокирует сохранение. Это техническая проверка формата/уникальности, ручной VALID остаётся отдельным статусом. Конфликт при сохранении показывается у поля без верхнего технического дублирования exchange_uid/wallet_address. Размер статуса15px на мобильном и десктопе.

При первом заполнении профиля (нет сохранённого кошелька и rewards) checkbox UID включён по умолчанию. При включённом checkbox UID и хэш вывода обязательны; пояснение предлагает заполнить UID либо отключить участие в Special Gift. При отключении показывается: «Отключая UID, вы отказываетесь от участия за специальные призы (Special Gift) от партнёра. Вы можете продолжить турнир за спортивный интерес и объявленные призы данной номинации». Отключение не снимает допуск к турниру. Сохранённое участие без UID при повторном открытии не переключается автоматически на партнёрское. Выбор категорий остаётся на сервере; контракт API и таблицы не меняются.

POST /api/v1/user/wallet, Bearer:

```json
{"wallet_address":"корректный адрес Solana","exchange_uid":null,"withdrawal_tx_hash":null}
```

При checkbox UID: exchange_uid — непустая строка, withdrawal_tx_hash — непустая строка. Адрес/хэш сохраняются в wallets, UID/категория — в partner_rewards, одной транзакцией. Новый либо изменённый кошелёк получает UNDER_REVIEW; изменённый UID — UNDER_REVIEW. Повтор идентичных уже проверенных данных не сбрасывает решение администратора.

Формат адреса проверяет система, валидность участия кошелька и UID — администратор. Signature и криптографическое доказательство владения не требуются. Изменение существующего адреса после start_at запрещено независимо от статуса кошелька и наличия scoring. Исключительный административный перенос не предлагается как обычная функция ЛК.

## 6. Публичный лидерборд

GET /api/v1/public/leaderboard без авторизации. Включает только APPROVED_AUTO/APPROVED_MANUAL и VALID кошелёк. Сортировка по числовому PNL DESC NULLS LAST, при равенстве — по user_id. ROI на порядок не влияет.

Ячейка участника: display_name, ниже первые 3 и последние 5 символов адреса через … и `| RespectGift` либо `| SpecialPartnerGift`. Следующие столбцы: стартовый капитал, текущая оценка портфеля, PNL с необязательным ROI. Последняя область пустая, в том же фоне; автоматический анализ подозрительных транзакций не реализован.

## 7. Подтверждение реализации

Над карточками «Показатели в турнире» размещены актуальные сроки. До закрытия регистрации: «Регистрация до», «Начало турнира», «Окончание турнира». После закрытия регистрации остаются две турнирные даты, после старта — только «Турнир до», после окончания — «Турнир завершён». Изменение состояния происходит автоматически по серверному расписанию. В админке все четыре даты доступны для просмотра независимо от публичного сокращения.

Общие карточки доступны также над таблицей публичного лидерборда и обновляются вместе с результатами. На главной гостя и участника размещён баннер «ДЕМО / Special gift»: техника Apple на XXX $ и суперприз, раскрываемый за три дня до окончания турнира. Сумма и партнёры пока не заданы; баннер является местом для будущего анонса и не меняет категорию награды участника.

Кнопка «В лидерборд» в блоке показателей показывается только в ЛК. На публичной главной и самом экране лидерборда она отсутствует. В шапке главной рядом со ссылкой «Лидерборд» — кнопка «Регистрация на турнир», открывающая существующую модальную форму в режиме регистрации (имя в турнире, Telegram username/ID, получение кода). До открытия или после закрытия регистрации кнопка недоступна с понятным пояснением. Логика кода, сессий, допуска и сохранения профиля остаётся прежней.

Над заголовком лидерборда — две строки: «METEORA $MET | PILOT TOURNAMENT» и «Liquidity Providers» (уточнённое владельцем написание). Все явно заданные мелкие размеры текста 7–14 px увеличиваются ровно в 1,5 раза, включая мобильные варианты; крупные заголовки и значения не масштабируются. Повторно к уже увеличенным значениям коэффициент не применяется. Проверяется читаемость и отсутствие обрезания на узком экране.

Отдельное уточнение логотипа: крупное «METEORA $MET» сохраняет размер; малая строка становится «PILOT TOURNAMENT» и сохраняет исходный размер до общего увеличения. Ниже подпись «Liquidity Providers» и выделенное жирным «by Meteora Plus Community», размер подписи увеличен на 50% от исходного; допускаются две строки. Это исключение для размеров двух верхних строк логотипа действует на главной и боковой панели.

Публичная главная получает GET /public/stats: число допущенных участников с VALID кошельком, сумму их текущего капитала, PNL и накопленного оборота LP. Значения NUMERIC выдаются decimal-строками, отсутствие данных — null/«—». Неполное покрытие отмечается числом участников с загруженным показателем. lp_volume не вычисляется из текущей суммы в позициях и не заменяет её; 100 открытий по 0,5 SOL дают 50 SOL оборота. Администратор добавляет показатель в обычную загрузку результатов; отсутствие поля сохраняет ранее загруженный оборот, явный null очищает его.

Серверные проверки: регистрация/вход, роль, нормализация, cooldown на 89/90 секундах и после рестарта, 30-минутный срок, окно продления, владелец callback, повтор/гонка/просрочка, logout, очистка кнопки, восстановление уже подтверждённого продления после исходного JWT exp.

Браузерные проверки: ЛК и публичный лидерборд, мобильный экран, сохранение входа при навигации/refresh/второй вкладке, баннер на 25-й минуте, подтверждение без нового кода, автоматический выход без подтверждения, сохранение countdown повторного кода. Изменяющие проверки выполняются только в отдельной временной БД с Telegram mocks.

Ручная финальная приёмка в реальном Telegram: код → вход → баннер → кнопка бота → продолжение ЛК; отдельный проход без подтверждения → новый вход. Спецификация фиксируется до этой приёмки; её результат добавляется в журнал проверки.
