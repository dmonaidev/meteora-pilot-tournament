# Требования и правила фронтенда

Актуальное функциональное поведение утверждено в [спецификации доступа, ЛК и правил 1.3](../product/access-and-cabinet.md), [контракте правил 1.0](../decisions/rules-v1.0.md) и [квалификации Special Gift 1.2](../decisions/partner-qualification-v1.2.md). [Экраны и права](../product/screens-and-access.md) описывают текущую реализацию. Сначала развернуть готовое решение, затем исправить фронтенд на основе существующих компонентов и CSS. Исправления отображения и вёрстки выполнять только с явного разрешения пользователя в пределах согласованной правки. Изменения сценариев, алгоритмов, API, структуры БД и данных требуют отдельного явного разрешения пользователя — владельца проекта. См. [границы исправлений](design-preservation.md).

## Визуальный бриф

Статус: для текущей локальной реализации владелец утвердил русский интерфейс и тёмный дизайн. Эти требования действуют при продолжении разработки. Новый исполнитель использует зафиксированные ответы; незаданные материалы уточняет только если они необходимы.

| Вопрос | Ответ |
| --- | --- |
| Название продукта и логотип | METEORA $MET / PILOT TOURNAMENT / Liquidity Providers / by Meteora Plus Community. Synergy и by Cryptus в интерфейсе запрещены владельцем. |
| Язык интерфейса | Русский, утверждён владельцем |
| Стиль, палитра, примеры сайтов | Тёмный дизайн, утверждён владельцем; зелёный акцент выбран для локального просмотра |
| Приоритет мобильной или десктопной версии | Адаптивная версия для обоих размеров |
| Готовый дизайн или дизайн на усмотрение агента | Готовый интерфейс утверждён; использовать текущий web/src без переработки |

Не требовать Figma или готовые исходники, если владелец поручает дизайн агенту. Не добавлять маркетинговые обещания, призы, условия участия или статистику, которых нет в требованиях. Бриф реализован и текущий внешний вид утверждён владельцем. Перенос не требует разработки нового дизайна.

## Обязательные экраны

1. Лендинг с регистрацией, входом и переходом к лидерборду.
2. Регистрация с display_name, обязательной незаполненной галочкой согласия с текущими опубликованными правилами, Telegram username/ID и шестизначным кодом; повторный вход без новой регистрации.
3. ЛК: регистрационный статус, кошелёк и хэш вывода, награда/UID, статусы ручной проверки и доступный scoring.
4. Публичный лидерборд.
5. Административный экран: восемь разделов, модерация, импорт реестра/метрик, расписание и редактор версий правил.

Дополнительные разделы, социальные механики, графики доходности и торговые функции не добавлять.

## Правила интеграции

- Единственный источник постоянного состояния — backend. Успех показывать после успешной записи; при ошибке сохранять введённые данные для исправления.
- Типы, ключи, enum и null соблюдать по API. API-клиент общий, схемы ответов проверяются; неожиданная форма ответа не исправляется угадыванием ключа.
- После записи перечитывать профиль/административный список. Старые запросы не должны затирать более новый экран; исключить повторное сохранение двойным кликом.
- Polling раз в 3 секунды, без перекрывающихся запросов; прекращать после успеха, истечения или закрытия окна.
- JWT использовать по контракту; при истечении предложить повторный вход. Не добавлять другой способ входа или refresh API без изменения спецификации.
- BOT_API_SECRET, bot token, JWT ключ, пароль БД и SSH ключ не входят во frontend bundle. Telegram ID брать из подтверждения бота, а не из произвольного поля пользователя.
- Административные действия доступны только при серверной проверке прав. Скрытая кнопка не заменяет проверку API; не вводить admin=true в запрос.
- Показывать ошибки поля и строки импорта. При WALLET_CHANGED/UID_CHANGED перечитать данные, не одобрять новые значения автоматически.

## Правила данных

- PNL — главный показатель, порядок строк получен с сервера. Не сортировать decimal как строку или через неточный Number; не менять порядок по ROI.
- Не вычислять PNL, ROI или допуск в браузере. ROI/капитал показывать только справочно; null — «—» или отсутствие справочной строки, но не ноль.
- Не ставить знак процента возле PNL. Единицу результата брать из согласованных настроек/текста проекта.
- wallet_address и withdrawal_tx_hash отправлять вместе. Не подключать wallet signing и не запрашивать signature.
- wallet_address_locked=true блокирует только смену существующего адреса. Хэш можно исправить; интерфейс объясняет повторную ручную проверку.
- При серверном WALLET_CHANGE_LOCKED перечитать профиль. Не предлагать исключительную смену кошелька ни пользователю, ни как обычную кнопку администратора.
- exchange_uid — строка, ведущие нули сохраняются. RESPECT передаёт null или не передаёт поле; пустую строку не отправлять.
- UID и хэш не публиковать в лидерборде. Тексты пользователя и причины отказов экранировать.
- При импорте scoring явно показать: отсутствующие справочные значения очищают предыдущие. Не делать скрытых формул и исправлений финансовых данных.

## Качество интерфейса

Адаптивная вёрстка для мобильного и десктопа; без горизонтального переполнения страницы. Для таблицы допустима отдельная горизонтальная прокрутка. Формы с видимыми подписями, доступом с клавиатуры и заметным фокусом. Статус обозначается текстом, а не одним цветом.

Для каждого запроса предусмотреть загрузку, успех, ошибку и пустые данные. Длинные адреса, хэши и имена не ломают экран. Успешный вход на телефоне должен позволять вернуться из Telegram на сайт без потери ожидающей сессии.

Проверить экраны на узком мобильном и широком десктопном размере, ошибки 401/403/409/410/422, null-поля, отрицательный PNL и момент начала турнира. Отдельно проверить реальный Telegram-переход на мобильном устройстве или явно указать, что такой тест ещё не выполнен.

## Уточнение владельца: разрешение и риск изменений

Запрещено самовольно менять алгоритмы, пользовательские сценарии, маппинг переменных между UI/API/ботом/БД, API-контракты, структуру БД и существующие записи. Сохранять имена полей, соответствия, типы, enum/null, единицы измерения и ведущие нули UID. Фронтенд менять только с явного разрешения пользователя в рамках согласованной правки. Развёртывание само по себе не разрешает менять фронтенд; разрешение менять фронтенд не разрешает менять защищённые части.

Если запрошенная пользователем правка может нарушить работу приложения, сценарии, алгоритмы, маппинг переменных, API или данные, до реализации предупредить пользователя: описать конкретные последствия и затронутые части, предложить безопасный вариант, запросить отдельное явное разрешение и дождаться ответа. Сам факт запроса правки и общее разрешение менять фронтенд не заменяют согласия на эти последствия.
