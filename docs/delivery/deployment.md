# Развёртывание на synergyhub.top

Инструкция для агента, которому поручены разработка и деплой. Подготовка этого документа сама по себе не означает, что сервер уже проверен или изменён.

## Целевая среда

| Параметр | Данные владельца |
| --- | --- |
| Домен | synergyhub.top |
| Сервер | YOUR_SERVER_IP |
| SSH пользователь | root |
| ОС | Ubuntu 24.04 |
| Тариф | Custom VIEs |
| Ресурсы | 4 cores, 8 GB RAM, 100 GB NVMe, подключение до 1 Гбит/с |
| Предложенный путь ключа | ~/.ssh/YOUR_DEPLOY_KEY |
| SSH опция | IdentitiesOnly=yes |

Ключ предоставляется отдельно. Путь относится к машине, с которой агент выполняет SSH; существование файла и доступность сети проверить. Содержимое ключа в чат, репозиторий и логи не выводить.

Пример подключения после получения ключа:

~~~sh
ssh -o IdentitiesOnly=yes -i ~/.ssh/YOUR_DEPLOY_KEY root@YOUR_SERVER_IP
~~~

Проверку ключа сервера не отключать. При несовпадении host key выяснить причину до подключения; не удалять запись known_hosts автоматически.

## Разрешение владельца

Владелец разрешил переиспользовать сервер под новый проект. Старый проект и его данные не нужны: относящиеся к нему приложения, БД, файлы, сервисы и конфигурацию разрешено удалить без резервного копирования. Владелец понимает необратимость удаления. Повторного разрешения на подтверждённые ресурсы старого проекта не запрашивать.

Пригодные reverse proxy, TLS, Docker, СУБД и настройки домена переиспользовать. Системные компоненты, SSH-доступ и ресурсы неизвестной принадлежности сохранять. Это разрешение не распространяется на случайные соседние проекты и все данные сервера целиком.

## Инвентаризация и границы удаления

1. Проверить фактическую ОС, свободное место/память, запущенные процессы, systemd units, контейнеры и compose-проекты, слушающие порты, proxy virtual hosts, сертификаты, приложения и базы.
2. Определить старый проект по совокупности признаков: домен, каталог приложения, compose labels, unit WorkingDirectory/ExecStart, подключаемая БД, upstream и volumes. Не считать принадлежность доказанной одним совпадением имени.
3. Сохранить в отчёте список конкретных целей и зависимостей без секретов. Для каждого удаления проверить фактический путь, symlink/mount, владельца ресурса и использование другими сервисами.
4. Удалять только установленные ресурсы старого проекта. Не применять глобальные prune, wildcard-удаление баз/томов, очистку всего /var/www, /opt или общих каталогов.
5. Общую СУБД сохранить; удалить только старую базу/роль, если не используются другими проектами. Общий proxy сохранить; заменить только относящийся к домену virtual host/upstream. Проверить конфигурацию перед reload.
6. Не удалять старый проект до готовой сборки нового, необходимых входных данных и рабочего способа запуска. Разрешение на удаление не требует создавать необязательный простой заранее.
7. Неизвестную принадлежность исследовать. Если ресурс действительно мешает и принадлежность установить нельзя, сохранить его и сообщить конкретный блокер с одним требуемым действием владельца.

В отчёте честно указать: восстановление удалённого старого проекта без бэкапа не предусмотрено. Возможность отката нового релиза не означает возможность вернуть старые удалённые данные.

## Порядок деплоя

1. Подготовить воспроизводимую сборку и зафиксировать версию кода. Выбрать порты и каталог по результатам инвентаризации.
2. Подготовить изолированные настройки нового приложения и PostgreSQL. Создать отдельные полномочия приложения; root SSH не означает запуск приложения с системными правами root.
3. Секреты хранить вне Git и публичного каталога, с ограниченным доступом. В отчёте перечислять имена переменных и путь конфигурации, не значения. Не выводить полные env/docker inspect и команды с токенами в лог.
4. Применить миграции штатной командой. Не использовать автоматический reset БД при обычном повторном запуске. Проверить постоянное хранилище и сохранение записей после перезапуска приложения.
5. Запустить backend и frontend как один продукт. Reverse proxy направляет /api/v1 на backend, остальные нужные пути на frontend; обновление SPA-страницы не возвращает 404. Бот запускается как управляемый процесс проекта и обращается к backend API.
6. Переиспользовать совместимую инфраструктуру; если её нет, установить минимально необходимую. Не менять глобальные версии СУБД и общие настройки без анализа соседних зависимостей.
7. Настроить надёжный автозапуск и рестарт через обнаруженную инфраструктуру systemd/Docker. БД доступна приложению, её порт не требуется публиковать в интернет.
8. Проверить DNS A/AAAA для synergyhub.top и фактический маршрут. Изменять записи только если мешают работе нового проекта. Не трогать MX/TXT и чужие поддомены. Для www ничего не предполагать: использовать только если решено обслуживать этот адрес.
9. Получить или переиспользовать действительный TLS сертификат домена; настроить HTTPS, HTTP → HTTPS и автоматическое продление. Не считать успешный локальный curl доказательством внешней доступности.
10. Выполнить проверки ниже. Когда все обслуживаемые ресурсы установлены и общий серверный контекст допускает безопасный перезапуск, проверить автозапуск контролируемой перезагрузкой и повторным SSH/HTTPS доступом. При наличии неизвестных соседних нагрузок не перезагружать сервер вслепую: проверить автозапуск сервиса и указать ограничение проверки перезагрузки.

## Проверки готовности

| Проверка | Доказательство |
| --- | --- |
| DNS и HTTPS | Домен разрешается правильно; действительная цепочка TLS; редирект с HTTP |
| Frontend | Основные страницы открываются извне и после прямого обновления URL; нет блокирующих ошибок браузера |
| API | Реальные ответы по контракту, ошибки авторизации, доступ участников/администратора разделён |
| Telegram | Реальный /start, подтверждение, polling, вход и повторный вход; без раскрытия токенов |
| PostgreSQL | Миграции применены, ограничения и запись/чтение работают, данные переживают рестарт |
| Турнир | Пара адрес/хэш, ручной допуск, импорт PNL, порядок leaderboard и граница T |
| Автозапуск | Сервисы восстанавливаются; результат проверки перезагрузки или конкретное ограничение записаны |
| Секреты | Отсутствуют в репозитории, frontend bundle, публичных ответах и отчёте |
| Эксплуатация | Записаны команды запуска, миграций, обновления, получения логов и пути конфигурации |

Не менять реальную дату турнира ради проверки границы T: использовать тестовую среду/управляемые часы. Для production smoke использовать контролируемые тестовые данные и убрать только созданные тестом записи, не затрагивая реальные загрузки администратора.

Если для реального Telegram-теста необходимо действие владельца, дать один конкретный шаг и не объявлять эту проверку пройденной до результата.
