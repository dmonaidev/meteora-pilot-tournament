## Первый этап: восстановить и запустить

Проверить, что выбранные каталоги свободны. Авторизоваться в GitHub для клонирования PRIVATE. Пример:

```sh
umask 077
git clone https://github.com/dmonaidev/meteora-pilot-tournament.git /opt/meteora-pilot-tournament
git clone https://github.com/dmonaidev/meteora-pilot-tournament-transfer.git /opt/meteora-pilot-private
chmod 700 /opt/meteora-pilot-private
install -m 600 /opt/meteora-pilot-private/config/deploy.env /opt/meteora-pilot-tournament/deploy/.env
cd /opt/meteora-pilot-tournament
git rev-parse HEAD
git -C /opt/meteora-pilot-private rev-parse HEAD
```

Сохранить оба SHA. config/deploy.env уже содержит действующий BOT_TOKEN, BOT_USERNAME, ADMIN_TG_IDS, 1800 секунд сессии, LOCAL_DEMO=false, production URL, новый пароль PostgreSQL и отдельные новые JWT_SECRET/BOT_API_SECRET. DATABASE_URL использует host db:5432 и тот же пароль. config/local-source.env нужен для сверки, а не запуска production. Не печатать env или развёрнутый docker compose config.

Фронтенд собирается Dockerfile из web/src: отдельно переносить dist не нужно. Node.js 24, PostgreSQL 17. Поднять только новую пустую БД:

```sh
docker compose --env-file deploy/.env -f deploy/compose.yml build
docker compose --env-file deploy/.env -f deploy/compose.yml up -d db
```

Дождаться healthcheck PostgreSQL. До восстановления не запускать app и демозаполнение. Импорт сам применяет миграции 001–010:

```sh
docker compose --env-file deploy/.env -f deploy/compose.yml run \
  --rm --no-deps --user 0:0 \
  -v /opt/meteora-pilot-private/data/application-data.json:/transfer/application-data.json:ro \
  app node scripts/handoff.mjs restore /transfer/application-data.json --fresh-database
```

Root нужен только разовому контейнеру для чтения защищённого файла; постоянное приложение использует штатного пользователя node. Snapshot уже включает публичные настройки. Не импортировать handoff/public-settings.json отдельно. При TARGET_DATABASE_NOT_EMPTY выяснить происхождение данных, не очищать БД автоматически.

Проверить сохранность: 3 профиля, 571 строка реестра, 2 кошелька, 2 записи UID/наград, 1 результат, название, четыре даты UTC, ссылка партнёра, редакции правил с UUID/статусами, допуск, ручные проверки, согласия и ведущие нули UID. Активные сессии и одноразовые коды не переносятся; пользователи входят заново.

```sh
docker compose --env-file deploy/.env -f deploy/compose.yml up -d app
curl --fail http://127.0.0.1:3000/health
```

Если порт 3000 занят, адаптировать привязку/upstream. Настроить virtual host synergyhub.top по deploy/nginx.conf.example, TLS, редирект HTTP → HTTPS и продление сертификата. Проверить DNS A/AAAA и внешнюю доступность. PostgreSQL в интернет не публиковать. Имя Compose-проекта synergyhub-tournament и постоянный том сохранять при обновлениях; down -v не применять.

```sh
sudo nginx -t
sudo systemctl reload nginx
curl --fail https://synergyhub.top/health
```

## Переключить существующего бота

Локальный polling при упаковке не остановлен. На один токен работает только один polling-процесс. Перед запуском серверного бота остановить прежний экземпляр. Если у агента нет доступа к компьютеру владельца, дать владельцу конкретный шаг для остановки. Новый бот не создавать, существующий webhook автоматически не удалять.

```sh
docker compose --env-file deploy/.env -f deploy/compose.yml --profile telegram up -d bot
```

Проверить /start и получение кода. Реальные сообщения проверки отправлять только владельцу/разрешённому тестовому аккаунту. Проверить через внешний HTTPS вход администратора/участника, кабинеты, правила, допуск, лидерборд, UTC/24 часа, 30-минутную сессию, её продление и сохранение после рестарта. Реальные записи и даты ради теста не менять.

## Второй этап: исправить фронтенд

После успешного развёртывания зафиксировать исходное состояние и резервную копию данных. Исправить отображение, загрузку ресурсов, читаемость, вёрстку и адаптивность готового web/src. Описание экранов и снимки приватного комплекта являются ориентирами, а не заданием на создание нового продукта.

Сохранить формы, поля, условия их появления, последовательность действий и роли. Не менять сервер, бот, алгоритмы, проверки, API, миграции, структуру БД, статусы, настройки и загруженные записи. Если исправление требует изменения этих частей, получить отдельное явное разрешение пользователя до реализации.

Проверить desktop 1440px и mobile 390px, существующие тесты на изолированной БД и отсутствие изменений рабочих данных. Передать URL, SHA обеих репозиториев, список исправлений фронтенда, результаты проверки, команды обновления/рестарта/backup без секретов. SSH-доступ передаётся отдельно только при его отсутствии у агента; остальные материалы уже в GitHub.

## Уточнение владельца: разрешение и риск изменений

Запрещено самовольно менять алгоритмы, пользовательские сценарии, маппинг переменных между UI/API/ботом/БД, API-контракты, структуру БД и существующие записи. Сохранять имена полей, соответствия, типы, enum/null, единицы измерения и ведущие нули UID. Фронтенд менять только с явного разрешения пользователя в рамках согласованной правки. Развёртывание само по себе не разрешает менять фронтенд; разрешение менять фронтенд не разрешает менять защищённые части.

Если запрошенная пользователем правка может нарушить работу приложения, сценарии, алгоритмы, маппинг переменных, API или данные, до реализации предупредить пользователя: описать конкретные последствия и затронутые части, предложить безопасный вариант, запросить отдельное явное разрешение и дождаться ответа. Сам факт запроса правки и общее разрешение менять фронтенд не заменяют согласия на эти последствия.

Обязательные инструкции Claude: [../../CLAUDE.md](../../CLAUDE.md). Это уточнение владельца имеет приоритет над прежними общими формулировками разрешения исправлять UI.
