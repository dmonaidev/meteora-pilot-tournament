# Перенос платформы на сервер

Развернуть готовую платформу METEORA $MET на synergyhub.top с сохранением настроек, участников и результатов. Исходники и публичные настройки находятся в GitHub; полная база, административные Telegram ID и секреты передаются отдельно закрытым каналом.

| Проверенный коммит функционального кода | b5120bc43800d3513c0833a2bf19ef31573a6f18 |
| Сервер | 147.45.41.148 |
| SSH пользователь | root |
| Домен | synergyhub.top |
| Заявленная ОС | Ubuntu 24.04, проверить фактически |
| Предложенный путь SSH ключа | ~/.ssh/meteora_deploy_r3 на машине агента |
| Telegram бот | @lptournamentsupport_bot |

Владелец передаёт SSH-ключ, действующий BOT_TOKEN и приватный архив `meteora-private-transfer.zip`. Архив содержит `application-data.json` и `runtime-settings.json`; токен бота в него не включён. Проверить наличие ключа; если предложенного файла нет, запросить фактический путь. Секреты не выводить в чат, логи и Git.

## Проверить сервер и документацию

```sh
ssh -o IdentitiesOnly=yes -i ~/.ssh/meteora_deploy_r3 root@147.45.41.148
```

Не отключать проверку ключа сервера. Проверить ОС, Docker/Compose, свободное место, занятые порты, существующие приложения, reverse proxy, DNS и сертификаты. Сохранить соседние сервисы. Не использовать глобальное удаление контейнеров, томов и каталогов. Общие конфигурации proxy не заменять целиком.

Прочитать `AGENTS.md`, `Agent.md`, `docs/README.md`, `docs/product/access-and-cabinet.md`, `docs/delivery/handoff.md` и `deploy/README.md`. Продукт уже реализован; применять утверждённые уточнения 0.3–1.3. Миграции и экспорт сохраняют существующие настройки и статусы.

## Подготовить приложение

Выбрать свободный каталог по результатам проверки. Пример ниже использует `/opt/meteora-pilot-tournament`; не перезаписывать существующий каталог неизвестного назначения.

```sh
git clone https://github.com/dmonaidev/meteora-pilot-tournament.git /opt/meteora-pilot-tournament
cd /opt/meteora-pilot-tournament
git rev-parse HEAD
cp deploy/.env.example deploy/.env
chmod 600 deploy/.env
```

Сохранить SHA разворачиваемой версии в отчёте. Коммит функционального кода указан выше; последующие изменения документации не требуют отката checkout к старому коммиту. Перед использованием более поздних изменений кода проверить их состав и результаты тестов.

Заполнить `deploy/.env` редактором или через защищённый механизм передачи секретов:

| Переменная | Источник или значение |
| --- | --- |
| BOT_TOKEN | Действующий токен владельца из локального .env, переданный закрытым каналом |
| BOT_USERNAME | Из runtime-settings.json |
| ADMIN_TG_IDS | Из runtime-settings.json; сохранить реальные административные ID |
| AUTH_JWT_TTL_SECONDS | 1800 |
| LOCAL_DEMO | false |
| PUBLIC_BASE_URL | https://synergyhub.top |
| BACKEND_URL | http://app:3000 |
| POSTGRES_PASSWORD | Новый случайный пароль, желательно hex для безопасного включения в URL |
| DATABASE_URL | postgresql://tournament:НОВЫЙ_ПАРОЛЬ@db:5432/tournament, пароль тот же, что POSTGRES_PASSWORD |
| JWT_SECRET | Новый случайный секрет минимум по 32 байта |
| BOT_API_SECRET | Другой новый случайный секрет минимум по 32 байта |

Не переносить localhost URL из `runtime-settings.json` в production. Даты, название, ссылка партнёра и правила находятся в БД и будут восстановлены из `application-data.json`.

## Восстановить полную базу

Разместить приватные файлы вне репозитория, например в `/opt/meteora-pilot-private`, с ограниченными правами: каталог 700, файлы 600. Не включать их в образ Docker, публичные Releases или Issues.

Сначала собрать приложение и запустить только новую БД:

```sh
docker compose --env-file deploy/.env -f deploy/compose.yml build
docker compose --env-file deploy/.env -f deploy/compose.yml up -d db
```

Дождаться готовности PostgreSQL по healthcheck. Не запускать приложение и демонстрационное заполнение до восстановления. Импорт требует пустую прикладную БД и сам применяет миграции 001–010.

```sh
docker compose --env-file deploy/.env -f deploy/compose.yml run \
  --rm --no-deps --user 0:0 \
  -v /opt/meteora-pilot-private/application-data.json:/transfer/application-data.json:ro \
  app node scripts/handoff.mjs restore /transfer/application-data.json --fresh-database
```

Root используется только разовым контейнером для чтения защищённого файла. Постоянное приложение запускается штатным пользователем образа `node`. Приватный файл примонтирован только для чтения.

Полный приватный файл уже содержит публичные настройки и правила. Не импортировать `handoff/public-settings.json` перед ним или после него. При отказе `TARGET_DATABASE_NOT_EMPTY` выяснить происхождение данных, не очищать БД автоматически.

Проверить состав восстановленного snapshot:

- 3 профиля, 571 запись реестра допуска;
- 2 кошелька и 2 записи наград/UID;
- 1 запись результата;
- название, четыре даты UTC с исходными секундами, реферальная ссылка;
- редакции правил с исходными UUID, статусами и архивом;
- статусы допуска и проверок, согласия участников и ведущие нули UID.

Активные сессии и одноразовые Telegram-коды не переносятся: участники входят заново. Профили и настройки сохраняются.

## Запустить сайт и HTTPS

```sh
docker compose --env-file deploy/.env -f deploy/compose.yml up -d app
curl --fail http://127.0.0.1:3000/health
```

Если порт занят, адаптировать привязку приложения и upstream. Настроить только virtual host `synergyhub.top` по `deploy/nginx.conf.example`: действительный TLS, редирект HTTP → HTTPS, автоматическое продление сертификата. Проверить DNS A/AAAA и внешнюю доступность. Не изменять MX/TXT и чужие поддомены. PostgreSQL не публиковать в интернет.

## Переключить Telegram бота

На один токен должен работать один polling-процесс. Локальный бот владельца при упаковке не останавливался. Перед серверным запуском установить и остановить прежний экземпляр. Если доступа к компьютеру владельца нет, сообщить ему конкретный шаг остановки. Существующий webhook автоматически не удалять; конфликтующие процессы не запускать параллельно.

После переключения:

```sh
docker compose --env-file deploy/.env -f deploy/compose.yml --profile telegram up -d bot
```

Новый бот создавать не требуется. Приложение и бот должны использовать один и тот же новый BOT_API_SECRET.

## Проверить и передать результат

Проверить внешний HTTPS, лидерборд, кабинет участника, админку, правила, ссылку партнёра, сохранение настроек после рестарта и отсутствие ошибок polling. Рабочие даты и реальные профили не менять ради тестов.

Время в интерфейсе — UTC, формат 24 часа. Сессия — 30 минут; за 5 минут до окончания появляется предложение продления через кнопку в Telegram. Повторная выдача кода — через 90 секунд. Проверить реальные вход и уведомление на согласованном аккаунте владельца; действия, требующие его телефона, дать одним конкретным шагом. Не объявлять Telegram проверенным до успешного прохода.

В отчёте указать URL, SHA, результаты восстановления, расположение конфигурации, команды запуска/обновления и способ резервного копирования новой PostgreSQL-базы. Указать результаты проверки автозапуска сервисов и внешнего HTTPS. Не перезагружать общий сервер без оценки соседних нагрузок.

Предыдущая локальная проверка: 89 серверных тестов, 11 браузерных сценариев, успешная сборка и круговой перенос полной базы на временном PostgreSQL. Проверка серверной среды выполняется отдельно после развёртывания; см. `docs/review/handoff-validation.md`.
