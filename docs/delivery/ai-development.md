# Пакет разработки для ИИ агента

Этот пакет запускает реализацию и развёртывание продукта на synergyhub.top. Продуктовый контракт — исходная версия 0.2.1 с приоритетными дополнениями 0.3–1.3. Действующая локальная реализация доступа, ЛК, расписания, дубликатов и правил описана в docs/product/access-and-cabinet.md и docs/decisions. Агент определяет техническую реализацию и распределение работы, сохраняет согласованные сценарии и доводит проект до работающего сервера.

Пакет рассчитан на нового пользователя и нового агента без истории исходного чата. Все необходимые продуктовые решения находятся в файлах. Новый пользователь передаёт пакет, запускает TASK_START.md и отдельно предоставляет доступы. Вопрос о визуальных требованиях задаёт исполнитель после запуска, а не автор пакета.

## Роли и полномочия

Оркестратор распределяет следующие обязанности между агентами, если среда поддерживает делегирование. При отсутствии такой возможности последовательно выполняет их сам. Дополнительное разрешение на распределение работы не нужно.

| Роль | Ответственность | Результат |
| --- | --- | --- |
| Оркестратор | Выбор стека, границы задач, зависимости, интеграция | Рабочий монолит, соблюдение контрактов |
| Backend | PostgreSQL, миграции, API, транзакции, авторизация | Сервер и интеграционные тесты |
| Bot | Telegram /start и подтверждение через API | Работающий бот, без прямого доступа к БД |
| Frontend | Публичные экраны, ЛК, административный экран | Интерфейс по отдельным требованиям и реальному API |
| Проверка | Критические сценарии и независимая сверка контрактов | Результаты AC с доказательствами |
| Развёртывание | Инвентаризация сервера, запуск, TLS, автозапуск | Доступный домен и эксплуатационная инструкция |

Назначения моделей — по Agent.md. Не выбирать неподдерживаемую модель молча: зафиксировать ограничение и использовать доступную подходящую модель без остановки независимой работы. Для каждой задачи указать владельца файлов, входной контракт и критерий завершения. Не поручать двум агентам одновременно менять один файл. Межмодульные изменения принимает оркестратор через реестр решений.

## Порядок исполнения

1. Изучить репозиторий и доступные настройки. Найти существующие исходники и пригодную инфраструктуру. Отсутствующие исходники создать по спецификации; не требовать от владельца готовую реализацию.
2. Выбрать простой поддерживаемый стек для одного приложения и PostgreSQL, учитывая сервер. Зафиксировать версии, структуру репозитория и короткое обоснование в architecture/implementation.md. Не вводить микросервисы, очереди, дополнительные продуктовые таблицы или новые функции без реальной необходимости и согласования изменения продукта.
3. Создать сборку, конфигурационный пример без секретов, миграции и тестовую БД. Реализовать DEV-01–09 из приёмки. Схемы запросов/ответов должны точно соответствовать API.
4. Делать backend, бот и тесты независимо от ожидания визуального брифа. Функциональные экраны и компоненты можно готовить по существующему контракту; оформление выполнять по ответу владельца в frontend-requirements.md. Не объявлять придуманный дизайн утверждённым.
5. Проверить реальные серверные запреты, транзакции, повторные запросы, конкурентные импорты, точность decimal, границу T, TTL и права. Моки Telegram допустимы для автоматических тестов, но не заменяют проверку реального входа.
6. Собрать frontend и backend, выполнить миграции на тестовой БД и прогон критериев. Подготовить релиз локально до очистки старого проекта.
7. Развернуть по deployment.md. Исправлять найденные проблемы до рабочего результата. Планы не отправлять вместо исполнения; давать короткие сообщения о фактическом ходе работы.
8. Сохранить отчёт реализации и эксплуатации, сообщить URL и результаты проверки либо точный блокер.

## Какие данные действительно нужны

| Параметр | Источник и действие |
| --- | --- |
| SSH ключ | Передаётся отдельно; предложенный путь ~/.ssh/YOUR_DEPLOY_KEY проверить на машине агента |
| Домен / адрес | synergyhub.top / YOUR_SERVER_IP; DNS и сервер проверить фактически |
| BOT_USERNAME и Telegram bot token | Найти относящуюся к проекту конфигурацию без вывода секретов; иначе запросить безопасную передачу |
| ADMIN_TG_IDS | Telegram User.id владельца/администраторов; не угадывать и не брать chat_id |
| TOURNAMENT_START_AT | Получить фактическую дату и время с часовым поясом, сохранить в UTC; не ставить пример из тестов |
| Единица PNL | Уточнить принятую единицу отображения, если не указана; не придумывать валютный символ |
| Бриф фронтенда | Отдельный ответ владельца, записывается в frontend-requirements.md |
| DNS доступ | Нужен только если записи требуют изменения; сначала проверить текущие записи |
| Внутренние секреты | JWT ключ, BOT_API_SECRET и пароль новой БД агент генерирует сам, безопасно сохраняет |
| Срок JWT | Агент выбирает техническое значение AUTH_JWT_TTL_SECONDS и документирует его |
| Исходный список и PNL | Загружает администратор после запуска; пустая БД не является блокером деплоя |

Не выводить существующие токены в отчёт и не копировать секреты в Git. Пользовательские данные, владельца бота и доступность ключа не выдумывать. Один запрос должен собирать только фактически отсутствующие входные данные; независимую работу продолжать.

## Что передать в результате

- Исходники frontend/backend/бота, зависимости с lockfile, миграции, команды сборки и запуска.
- .env.example с описаниями переменных без реальных значений.
- scripts или конфигурацию воспроизводимого деплоя, подходящую обнаруженному окружению; пригодную инфраструктуру переиспользовать.
- delivery/implementation-report.md: версия кода, статусы AC-01–73 (пройден / не пройден / не проверен), команды проверок, ограничения. Не выдавать непроверенный пункт за пройденный.
- delivery/operations.md: сервисы, расположение приложения и конфигурации без значений секретов, миграции, обновление, логи, автозапуск, DNS/TLS и возврат к предыдущему релизу нового приложения, если доступен.
- Рабочие HTTPS frontend/API и бот; результаты реального входа, записи данных, загрузки PNL и лидерборда. В production не оставлять синтетические результаты турнира.

Готовность означает соответствие спецификации и подтверждённую работу после развёртывания. Запуск процесса без проверки пользовательского пути не считается завершением.
