# Backend: действующий контракт 0.3

Проверка: `node scripts/test.mjs` — **10 тестов пройдено, 0 ошибок, 0 пропусков**, включая отдельный тест оркестратора для закрытого исключения кошелька. Использована настоящая PostgreSQL 17.10; каждый набор работает в отдельной временной схеме. Деплой не выполнялся.

Прогон `tests/backend.test.mjs` подтверждает:

- Семь таблиц после двух последовательных миграций; singleton tournament_settings с начальной датой null. ENV TOURNAMENT_START_AT не читается и не требует корректного значения.
- Public/admin settings возвращают постоянную дату; назначение, очистка и повторное назначение до старта разрешены. Прошедшая/невалидная дата отклоняется; после старта исправление и очистка дают TOURNAMENT_ALREADY_STARTED.
- Пересоздание buildApp читает прежнюю дату. При удерживаемой эксклюзивной блокировке настроек запись кошелька ждёт, не удерживает user lock, затем видит наступивший старт и запрещает смену. Проверены T−1, T+1 и одинаковая пара после старта.
- Необязательный username сохраняется в ожидающей сессии; несовпадение даёт TELEGRAM_ACCOUNT_MISMATCH без users и без is_used. Совпадение с иным регистром разрешено как для регистрации, так и для входа. Старые запросы без username работают.
- Кошелёк без UID принимается без хэша, возвращает hash=null и валидируется администратором с null. Непустой hash без UID запрещён; UID без hash отклоняет всю операцию, оставляя wallet/rewards=null.
- Общая форма wallet атомарно записывает UID/hash. reward_type в пользовательском запросе запрещён. Сервер задаёт PARTNER_GIFTS либо RESPECT; одинаковый UID сохраняет VALID; снятие UID очищает hash и возвращает кошелёк на проверку.
- Альтернативная rewards-операция требует существующий кошелёк для UID, принимает hash и меняет пару атомарно; очистка UID очищает hash. Администратор сравнивает адрес и nullable hash с текущими значениями.
- После изменения hash существующего VALID кошелька статус UNDER_REVIEW, причина null, scoring скрыт в профиле и сохранён в SQL. INVALID кошелёк без scoring блокирует смену адреса после старта.
- Public leaderboard публикует wallet_address и точный разрешённый набор ключей, скрывает UID/hash/Telegram/notes, использует SpecialPartnerGift и RespectGift. Проверены числовая сортировка, null-last, ноль выше отрицательного PNL, равные PNL с различными ROI и users.id как второй ключ.
- Конкурентные initial/scoring импорты возвращают корректные inserted/updated; неверные строки и дубли откатываются; ручной допуск и исходное имя сохраняются; готовые PNL/ROI не вычисляются из капитала.
- TTL ровно 900 секунд оставляет is_used=false; истёкший JWT и неверный секрет отвергаются; участник не получает admin API. Rate limit даёт 429 до записи в БД; LOCAL_DEMO запрещён в production и на нелокальном HOST.

События для уведомлений выставляются после успешного COMMIT. Отдельный PostgreSQL-тест проверил однократное событие новой регистрации, отсутствие события при повторном verify/регистрации и идентичном VALID кошельке, отсутствие события после реального rollback с тестовым SQL-trigger, а также события ручной модерации и scoring. Доставка сообщений выполняется отдельным модулем бота.

Реальный Telegram вход и доставка сообщений требуют отдельной проверки с настроенным токеном. UI проверяется отдельно. Следующая матрица сохранена как история контракта **0.2.1**: обязательный hash, выбор reward_type, метка с пробелами, ENV-дата и запрет публикации адреса отменены документом current-contract-v0.3.md; эти отменённые варианты не считаются требованиями текущего прогона.
