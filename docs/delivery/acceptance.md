# Задачи и приёмка криптотурнира

Версия 0.2.1. Junior получает задачи со ссылками на сценарии, API, переменные и алгоритмы. Функция готова, когда её поведение совпадает с документами, а не только когда экран открывается.

## Порядок реализации

| Задача | Содержание | Связи | Критерий |
| --- | --- | --- | --- |
| DEV-01 | Каркас приложения и шесть таблиц | database.md | PK/FK/UNIQUE работают; нет новых таблиц |
| DEV-02 | Регистрация, bot/verify, polling и JWT | SC-01–03, ALG-01–03 | Один профиль, правильный допуск и TTL |
| DEV-03 | ЛК и повторный вход | SC-02, SC-11, ALG-10 | Собственные данные, корректные null и статусы |
| DEV-04 | Импорт initial_users и ручной допуск | SC-04, SC-09, ALG-04/07 | Импорт не отменяет ручные решения |
| DEV-05 | Адрес, хэш вывода, ручная проверка и блокировка после старта | SC-05–06, ALG-05 | Нет подписи; пара сохраняется; смена после старта запрещена |

## Данные для приёмки

| Пользователь | Telegram ID | Есть в initial_users | Начальное состояние |
| --- | --- | --- | --- |
| A | 100001 | Да | Нет users |
| B | 100002 | Нет | Нет users |
| C | 100003 | Да | Уже users с REJECTED и admin_notes |
| D | 100004 | Нет | APPROVED_MANUAL, wallet VALID |
| E | 100005 | Да | APPROVED_AUTO, wallet INVALID |
| F | 100006 | Нет | PENDING_VALIDATION, wallet VALID |

Имена и ID синтетические, не реальные аккаунты. Для реального E2E Telegram использовать отдельные контролируемые тестовые аккаунты. В тестах бота проверить null username и различие message.from.id/chat.id.

Строка D: обязательный pnl=100.000000; администратор может также передать initial=1000.000000, current=1100.000000, positions=300.000000, roi_percentage=10.0. Значения готовы до загрузки. Сайт не проверяет их процентной формулой и не рассчитывает PNL из capital.

Для времени использовать тестовую границу T=TOURNAMENT_START_AT и проверки T−1 секунду/T/T+1 секунду. Не назначать этим тестом фактическую дату турнира.

## Сквозная приёмка

Новый B регистрируется → PENDING_VALIDATION → вводит адрес, хэш вывода с биржи и PARTNER_GIFTS UID → админ одобряет регистрацию и пару wallet/hash → загружает PNL без обязательного ROI → B появляется по месту PNL с RespectGift → админ подтверждает UID → метка становится Special Partner Gift → наступает T → смена адреса блокируется → админ отзывает допуск → B исчезает, готовые результаты сохраняются.

Этот сценарий должен пройти через реальные серверные проверки и БД. UI не имитирует допуск локальным состоянием. Ревью проверяет совпадение ключей API со словарём, обработку null и отсутствие незаявленных источников скоринга.
