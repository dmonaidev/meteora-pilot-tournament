1. ОБЪЯВЛЕННЫЕ БАЗЫ ДАННЫХ И ПЕРЕЧЕНЬ ПОЛЕЙ (POSTGRESQL)
--------------------------------------------------------------------------------

Таблица 1: initial_users (Справочник "белого списка" от администратора)
* Назначение: Хранение первичного списка участников, импортированного админом из CSV.
* Поля:
  - tg_id (BigInt, Primary Key) — Жесткий ID Telegram пользователя для сверки.
  - tg_username (Varchar(255), Nullable) — Юзернейм пользователя (очищенный от @).
  - group_name (Varchar(100), Not Null) — Роль пользователя (ученик, команда, бот).
  - subgroup_1 (Varchar(255), Nullable) — Экосистема (колонка CommunityEcosystem).
  - subgroup_2 (Varchar(255), Nullable) — Статус подписки (колонка MeteoraPlus).
  - subgroup_3 (Varchar(255), Nullable) — Поток обучения (колонка MeteoraPro).
  - system_notes (Text, Nullable) — Исходные примечания админа из файла.

Таблица 2: users (Основная таблица профилей и авторизованных сессий)
* Назначение: Учетные записи верифицированных участников и их текущий статус допуска.
* Поля:
  - id (UUID, Primary Key) — Внутренний системный ID профиля пользователя.
  - tg_id (BigInt, Unique, Not Null) — Связующий ID с Telegram-ботом.
  - tg_username (Varchar(255), Nullable) — Текущий актуальный юзернейм участника.
  - display_name (Varchar(100), Not Null) — Публичное имя игрока для Лидерборда.
  - registration_status (Enum, Not Null) — Статус допуска к турниру. 
    Значения: 'APPROVED_AUTO', 'APPROVED_MANUAL', 'PENDING_VALIDATION', 'REJECTED'.
  - admin_notes (Text, Nullable) — Обязательный комментарий админа при ручном изменении.

Таблица 3: wallets (Модуль криптокошельков участников)
* Назначение: Хранение адресов кошельков Solana и результатов их валидации.
* Поля:
  - id (UUID, Primary Key) — ID записи кошелька.
  - user_id (UUID, FK to users.id, Unique) — Связь с пользователем (1 юзер = 1 кошелек).
  - wallet_address (Varchar(44), Not Null) — Адрес кошелька Solana в формате Base58.
  - validation_status (Enum, Not Null, Default: 'UNDER_REVIEW') — Статус проверки.
    Значения: 'UNDER_REVIEW', 'VALID', 'INVALID'.
  - rejection_reason (Text, Nullable) — Причина отказа (отображается пользователю в ЛК).

Таблица 4: partner_rewards (Модуль выбора типа наград и интеграции с биржей)
* Назначение: Сбор UID биржи для участников, претендующих на ценные призы.
* Поля:
  - user_id (UUID, FK to users.id, Primary Key) — Системный ID участника.
  - reward_type (Enum, Not Null) — Выбор пользователя. Значения: 'RESPECT', 'PARTNER_GIFTS'.
  - exchange_uid (Varchar(50), Nullable) — Идентификатор (UID) на бирже партнера.
  - uid_status (Enum, Not Null, Default: 'UNDER_REVIEW') — Статус проверки UID админом.
    Значения: 'NOT_REQUIRED' (если Респект), 'UNDER_REVIEW', 'VALID', 'INVALID'.

Таблица 5: tournament_scoring (Аналитические метрики капитала и скоринга)
* Назначение: Хранение финансовых показателей участников для Лидерборда.
* Поля:
  - user_id (UUID, FK to users.id, Primary Key) — Системный ID участника.
  - initial_capital (Numeric(20,6), Default: 0) — Стартовый капитал (с возможностью оверрайда).
  - current_capital (Numeric(20,6), Default: 0) — Текущий совокупный баланс (SOL + SPL).
  - in_positions_amount (Numeric(20,6), Default: 0) — Объем средств внутри позиций/пулов.
  - roi_percentage (Float, Default: 0) — Процент доходности (вычисляется автоматически).

Таблица 6: pending_sessions (Временный буфер авторизации для связки Сайт <-> Бот)
* Назначение: Синхронизация действий пользователя на фронтенде и в Telegram-боте.
* Поля:
  - token (Varchar(64), Primary Key) — Уникальный токен ссылки (reg_XXX или auth_YYY).
  - session_type (Enum, Not Null) — Тип сессии. Значения: 'REGISTRATION', 'AUTHORIZATION'.
  - display_name (Varchar(100), Nullable) — Имя, введенное на сайте до подтверждения ТГ.
  - tg_id (BigInt, Nullable) — Заполняется ботом после перехода пользователя по ссылке.
  - is_used (Boolean, Default: false) — Флаг завершения сессии.
  - created_at (Timestamp, Default: NOW()) — Время жизни токена (15 минут).

2. ПРАВИЛА И АЛГОРИТМ ИМПЛЕМЕНТАЦИИ (USER FLOW И СВЯЗКА ПРОЦЕССОВ)
--------------------------------------------------------------------------------

Сценарий А: Полный путь Регистрации нового пользователя
1. Пользователь заходит на Лендинг, нажимает кнопку "Регистрация" и вводит желаемый `display_name`.
2. Фронтенд отправляет данные на бэкенд. Бэкенд генерирует случайный уникальный токен и делает запись в таблицу `pending_sessions` (`session_type = 'REGISTRATION'`).
3. Фронтенд сайта открывает модальное окно и генерирует кнопку-ссылку в бота: `https://t.me` (где reg_123456 — сгенерированный токен).
4. Фронтенд запускает пуллинг (опрос) эндпоинта проверки сессии каждые 3 секунды, ожидая подтверждения от бота.
5. Пользователь переходит в Telegram и нажимает кнопку [Старт]. Бот считывает аргумент запуска (`reg_123456`) и получает реальные `tg_id` и `tg_username` пользователя.
6. Бот шлет JSON-запрос на бэкенд сайта через защищенный эндпоинт верификации.
7. Логика бэкенда при обработке запроса от бота:
   - Бэк проверяет наличие `tg_id` в таблице `initial_users` (Белый список).
   - ЕСЛИ НАЙДЕН: В таблице `users` создается постоянный профиль, статус `registration_status = 'APPROVED_AUTO'`.
   - ЕСЛИ НЕ НАЙДЕН: В таблице `users` создается постоянный профиль, статус `registration_status = 'PENDING_VALIDATION'`.
   - В таблице `pending_sessions` для токера `reg_123456` проставляется реальный `tg_id` и флаг `is_used = true`. Бот выводит пользователю соответствующий текст (Успешно или Ожидайте модерации).
8. Фронтенд сайта при очередном пуллинге видит, что сессия успешно обработана, получает от бэкенда авторизационный JWT-токен пользователя и автоматически рендерит Личный Кабинет (Мини-кабинет).

Сценарий Б: Повторный вход (Авторизация)
1. Пользователь нажимает на сайте кнопку "Вход".
2. Бэкенд создает запись в `pending_sessions` с типом `AUTHORIZATION` и токеном `auth_7890`. Сайт перенаправляет юзера в бота по ссылке `?start=auth_7890`.
3. Юзер нажимает [Старт], бот передает токен и `tg_id` на бэк.
4. Бэк находит пользователя в таблице `users` по `tg_id`, помечает временную сессию использованной. Фронтенд сайта фиксирует это, авторизует сессию и открывает Личный Кабинет.

3. МИГРАЦИЯ ДАННЫХ И НАПРАВЛЕНИЯ ПОТОКОВ (ФРОНТЕНД / БЭКЕНД)
--------------------------------------------------------------------------------

Потоки данных ЛК (Мини-Кабинета) -> GET /api/v1/user/profile:
Фронтенд запрашивает профиль и получает единый синхронизированный JSON. Интерфейс ЛК адаптируется под полученные статусы:
* ЕСЛИ `registration_status == 'PENDING_VALIDATION'`: ЛК отображает предупреждение: "Ваш аккаунт отсутствует в списках и находится на ручной модерации у администратора. Вы можете продолжить заполнение данных ниже, доступ к турниру откроется после одобрения".
* Поля ввода кошелька Solana и UID биржи доступны пользователю ВСЕГДА (даже если статус регистрации PENDING).
* Данные кошелька уходят из ЛК на бэк, создавая запись в `wallets` со статусом `UNDER_REVIEW`. При отклонении админом юзер видит статус `INVALID` и причину `rejection_reason`, поле ввода становится доступно для повторной отправки.
* Блок турнирного скоринга (`scoring`) скрыт в ЛК до тех пор, пока `wallets.validation_status` не примет значение `VALID`.

Потоки данных Лидерборда:
Формирование Лидерборда происходит динамически на стороне бэкенда через SQL-представление (View).
* Правило жесткой фильтрации: В Лидерборд попадают ТОЛЬКО пользователи, у которых одновременно:
  `users.registration_status IN ('APPROVED_AUTO', 'APPROVED_MANUAL')` И `wallets.validation_status = 'VALID'`.
* Вычисление тегов на бэквокале: На бэкенде при сборке Лидерборда проверяется таблица `partner_rewards`. Если `reward_type == 'PARTNER_GIFTS'` и `uid_status == 'VALID'`, игроку присваивается текстовая метка "Special Partner Gift". Во всех остальных случаях (выбран респект, UID не валиден или еще проверяется) присваивается метка "RespectGift". На фронтенд лидерборда данные уходят в готовом отсортированном виде.

4. МАРШРУТЫ API (ENDPOINTS) ДЛЯ ИНТЕГРАЦИИ СИСТЕМЫ
--------------------------------------------------------------------------------

1. Модуль Telegram-бота:
* POST /api/v1/bot/verify — отправка ботом данных сессии.
  Запрос: { "token": "reg_123456", "tg_id": 70000002, "tg_username": "PrivateAccount_003" }
  Ответ: { "status": "success", "registration_status": "APPROVED_AUTO"/"PENDING_VALIDATION" }

2. Модуль Личного Кабинета (Требует заголовка Authorization: Bearer JWT):
* GET /api/v1/user/profile — получение всех данных и статусов мини-кабинета.
* POST /api/v1/user/wallet — отправка адреса Solana кошелька.
  Запрос: { "wallet_address": "4k3Dyjzvzp8eTuYuJpRSN9r7TfS1iv4m", "signature": "hex_string" }
* POST /api/v1/user/rewards — выбор призов и ввод UID.
  Запрос: { "reward_type": "PARTNER_GIFTS", "exchange_uid": "88771122" }

3. Публичный Лидерборд (Открытый роут):
* GET /api/v1/public/leaderboard — возвращает массив допущенных участников с вычисленными ROI и метками призов.

4. Панель Администратора (Доступ строго с флагом роли admin):
* POST /api/v1/admin/users/moderate — одобрение/отклонение пользователей на ручной валидации.
  Запрос: { "tg_id": 99999, "action": "APPROVE"/"REJECT", "admin_notes": "Текст" }
* POST /api/v1/admin/wallets/validate — модерация кошельков участников.
