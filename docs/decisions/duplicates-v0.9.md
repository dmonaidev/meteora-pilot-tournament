# Контракт 0.9 — проверка дубликатов кошелька и UID

Поручение владельца: обнаруживать дубликаты непосредственно при заполнении полей кошелька и UID. Существующие права, ручная валидация и категории наград сохраняются.

## База и сохранение

Миграция007 добавляет уникальный индекс `wallets_wallet_address_unique` на wallets.wallet_address и уникальный индекс `partner_rewards_exchange_uid_unique` на partner_rewards.exchange_uid WHERE exchange_uid IS NOT NULL. Адрес сравнивается точно с учётом регистра Base58; UID — после существующего trim, точно, строкой, с сохранением ведущих нулей. Проверяются все сохранённые строки независимо от допуска и статуса проверки. Собственное значение того же user_id разрешено. Null UID не ограничивается.

До миграции обнаруженные существующие дубликаты нельзя молча удалять/перепривязывать. Локальная база проверена read-only: 0 групп дубликатов кошельков и UID. Реальные участники и демозапись сохраняются.

POST /user/wallet и POST /user/rewards обеспечивают проверку до записи и окончательную защиту уникальными индексами при гонке. Изменение кошелька/хэша/UID одной операции атомарно: конфликт откатывает всё. Ошибки409: `WALLET_ALREADY_REGISTERED` либо `UID_ALREADY_REGISTERED`, с error.fields `{field:'wallet_address'|'exchange_uid',message:'Этот кошелёк уже зарегистрирован другим участником'|'Этот UID уже зарегистрирован другим участником'}`. Уникальные конфликты этих двух индексов преобразуются в указанные API-ошибки, не500. Чужие имя/ID/Telegram/кошелёк по UID не возвращаются.

## API проверки при вводе

POST /api/v1/user/profile-check, действующий Bearer. Непустой строгий объект с одним или двумя полями: `{wallet_address?:валидный Solana адрес,exchange_uid?:непустая строка max50}`. Trim/формат совпадает с сохранением. Invalid/пустой/лишний параметр —422; нет авторизации —401. Лимит120 запросов/мин на IP перед чтением БД.

Ответ200 всегда содержит оба ключа: `{wallet_address:null|{available:boolean},exchange_uid:null|{available:boolean}}`; null — поле не проверялось. available=false только если значение уже сохранено другим user_id. Это read-only запрос, не резервирует значения и не меняет статусы. Нет данных владельца или его статусов.

## UI

Проверять заполненное корректное поле после500мс паузы, не требуя заполненного хэша и нажатия «Сохранить». Для адреса сначала локально проверить Base58/32байта; для UID — trim, непустое значение/max50. Отключённый UID не проверяется. Результат под соответствующим полем, aria-live: «Проверяем…», «Этот кошелёк уже зарегистрирован другим участником» / «Этот UID уже зарегистрирован другим участником», либо «Дубликатов нет». Ошибка сети явно говорит о невозможности проверки, не объявляет значение свободным.

Изменение поля немедленно снимает старый результат; устаревший ответ не применяется (AbortController + сверка текущего значения/поколения). Переключение UID/смена профиля отменяет прежний запрос. При обнаруженном дубликате или незавершённой проверке непустого корректного значения сохранение блокируется. Ошибка сетевой проверки разрешает повторную попытку сохранения с окончательной серверной проверкой, без утверждения о свободном значении. При конфликте сохранения также показать сообщение у поля. Собственное сохранённое значение не блокировать.

## Проверки

Уточнение интерфейса от08.10.2026: сразу после ввода показывать результат под соответствующим полем. Корректное непустое значение — «Проверяем на дубликаты…», затем «Проверено: дубликатов нет» или сообщение о занятом кошельке/UID. Некорректный формат адреса показывать у поля и блокировать сохранение. Сетевой сбой не означает валидность. Проверка формата/уникальности не заменяет ручной VALID администратора. При конфликте сохранения сообщение выводится у поля без дублирующего технического блока exchange_uid/wallet_address. Кнопки отдельного запуска проверки нет.

Отдельная временная БД: доступ/валидация/лимит/privacy precheck, собственные/чужие/null значения, оба пути сохранения, откат пары и конкурентные записи одного адреса или UID (один успех, один409), идемпотентная миграция. Старые тесты использовать уникальные адреса для разных владельцев, сохраняя исходные сценарии; намеренно дублирующие данные перенести в новые отрицательные проверки.

Браузер: дубликат появляется во время ввода даже при пустом хэше, блокирует кнопку; смена значения убирает устаревшую ошибку, собственные данные разрешены. Реальные профили не менять при QA. Только локальная разработка.
