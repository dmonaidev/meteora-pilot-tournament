# Контракт уточнений владельца версии 0.3

Принят оркестратором 8 октября 2026 года на основании последних указаний владельца. Этот документ имеет приоритет над противоречащими ему формулировками 0.2.1. Реализация выполняется локально; деплой сейчас не поручен.

## Название и оформление

Единственное название продукта: Meteora $MET Tournament by Meteora Plus Community. Чёрный фон, яркий зелёный акцент и фиолетовые детали по референсам. Запрещено использовать старую атрибуцию из референса и Synergy как бренд интерфейса. Экранные тексты и навигация относятся только к турниру.

## Дата турнира

Дата хранится в единственной строке tournament_settings: id=1, start_at TIMESTAMPTZ NULL. Эта седьмая таблица добавлена только для явно запрошенной постоянной административной настройки. Первоначальное значение null; запуск без даты разрешён. TOURNAMENT_START_AT больше не является источником правила и не обязателен.

GET /api/v1/public/tournament и GET /api/v1/admin/tournament/settings возвращают {start_at: string|null, started: boolean, server_time: ISO UTC}. Публичная форма не содержит административных данных. POST /api/v1/admin/tournament/settings принимает {start_at: string|null}; до старта дата может быть назначена, исправлена или очищена. Новая непустая дата должна быть валидной будущей UTC ISO датой. После now >= текущий start_at любые обычные изменения, включая очистку, возвращают 409 TOURNAMENT_ALREADY_STARTED. Административный POST блокирует строку настроек и проверяет время после блокировки.

wallet_address_locked = wallet существует AND start_at != null AND now >= start_at. При записи кошелька сервер читает настройку под совместимой блокировкой до блокировки users, чтобы конкурентное назначение даты не обходило правило. Дата не может автоматически стать неназначенной при рестарте.

## Telegram вход

Используется разрешённый владельцем вариант со ссылкой в Telegram-бота, без пароля и без email. На форме отображается Telegram username. POST /auth/register принимает display_name и необязательный tg_username; POST /auth/login принимает необязательный tg_username. Если username задан, нормализованное значение сохраняется в pending_sessions.expected_tg_username и при bot/verify сравнивается с настоящим message.from.username без учёта регистра. Несовпадение → 409 TELEGRAM_ACCOUNT_MISMATCH без привязки. Сам username не доказывает личность: ID и актуальный username поступают только от бота. Старые запросы без username допустимы. Подтверждённая ссылка продолжает работать через существующий polling; отдельный парольный или кодовый механизм не добавляется.

## UID и условный хэш

Пользователь не выбирает reward_type. В форме есть отметка «Указать UID аккаунта на бирже». exchange_uid — строковый UID биржи, не UUID пользователя. При отметке UID и withdrawal_tx_hash обязательны. Без отметки оба значения null; адрес кошелька остаётся обязательным. wallets.withdrawal_tx_hash теперь nullable.

POST /api/v1/user/wallet принимает wallet_address, необязательный withdrawal_tx_hash (string|null) и необязательный exchange_uid (string|null). Если exchange_uid не передан, используется существующий UID. Если передан, сервер атомарно обновляет участие партнёра вместе с кошельком. Эффективный непустой UID требует непустого хэша; без UID допустим только отсутствующий/null хэш и в БД сохраняется null. Форма всегда передаёт exchange_uid явно. При снятии отметки очищаются UID и хэш, reward_type=RESPECT, uid_status=NOT_REQUIRED. Изменение пары адрес/хэш отправляет кошелёк на UNDER_REVIEW; готовый scoring сохраняется. Обычная блокировка адреса после старта действует независимо от UID.

POST /api/v1/user/rewards сохраняется как альтернативная операция: принимает exchange_uid (string|null) и необязательный withdrawal_tx_hash, без reward_type. Для ненулевого UID требует уже поданный кошелёк и существующий/поданный непустой хэш; если их нет → 422. Хэш/награда обновляются в той же транзакции под users lock. Снятие UID очищает хэш. Клиент использует общую форму user/wallet, поэтому первоначальная подача выполняется атомарно.

reward_type назначает сервер: UID отсутствует → RESPECT; UID присутствует → PARTNER_GIFTS. Новый/изменённый UID → UNDER_REVIEW; идентичный сохраняет uid_status. Подтверждение администратором делает публичный reward_tag=SpecialPartnerGift; во всех остальных случаях RespectGift. Категория не является редактируемым пользовательским полем. Администратор проверяет UID обычным admin/rewards/validate.

admin/wallets/validate принимает проверенный withdrawal_tx_hash как string|null и сравнивает его с текущим значением, включая null. Кошелёк без UID валидируется по адресу без обязательного хэша. Хэш с UID по-прежнему проверяется вручную.

## Лидерборд

Доступен гостю. Публичный JSON дополнен wallet_address; это адрес уже допущенного участника, по явному указанию владельца. Хэш, UID, Telegram ID/username и заметки остаются приватными. Первая строка ячейки — display_name, вторая меньшим шрифтом — первые 3 и последние 5 символов адреса через разделитель | и reward_tag. Значения метки: RespectGift и SpecialPartnerGift.

Колонки: участник; initial_capital; current_capital; PNL (ROI справочно внутри той же ячейки); пустая область в фоне таблицы. Сортировка по числовому pnl DESC NULLS LAST, затем user_id ASC; ROI сохраняет справочный смысл и не меняет порядок. Пустая область не имеет заголовка с пугающим текстом и не вводит механизм предупреждений в этом этапе.

## Реестр

Предоставленный Excel используется для первоначального импорта initial_users. Импорт исходника не создаёт users и не затирает ручные решения. Два реальных администратора задаются серверной конфигурацией ADMIN_TG_IDS; username — поясняющая информация, права проверяются по ID.
