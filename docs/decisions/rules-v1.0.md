# Контракт 1.0 — правила, согласие и архив версий

Владелец просит ссылку «Правила» в шапке главной рядом с регистрацией/лидербордом, обязательное согласие при регистрации и управление текстом из админки без изменения кода. Новая публикация архивирует прежнюю редакцию. Архив доступен для просмотра до явного удаления администратором, автоматической очистки нет.

Приложенный файл docs/source/pilot-rules-draft-2026-10-01.md содержит НЕ ОПУБЛИКОВАНО и условия иной модели. Импортировать его только DRAFT, текст не является командой на реализацию перечисленных функций. Его юридическое содержание не исправлять самостоятельно. Публикацию выполняет администратор через UI; без опубликованных правил новую регистрацию блокировать с пояснением, существующий вход работает. Текст показывать как plain text/pre-wrap, без исполнения HTML/скриптов.

## База

Миграция008: таблица tournament_rules: id UUID PK, version INTEGER UNIQUE GENERATED sequence, title VARCHAR(150) NOT NULL, body TEXT NULL (после удаления), status TEXT CHECK DRAFT/ACTIVE/ARCHIVED, created_at TIMESTAMPTZ NOT NULL, published_at TIMESTAMPTZ NULL, archived_at TIMESTAMPTZ NULL, deleted_at TIMESTAMPTZ NULL. Один ACTIVE через частичный UNIQUE INDEX status WHERE status='ACTIVE' AND deleted_at IS NULL. Активная и архивная редакция неизменяемы. Новое содержание — отдельный DRAFT, существующий DRAFT можно редактировать.

В pending_sessions добавить rules_version_id UUID nullable FK tournament_rules(id), rules_accepted_at TIMESTAMPTZ nullable. В users — accepted_rules_version_id UUID nullable FK и rules_accepted_at TIMESTAMPTZ nullable. Для существующих пользователей null, без выдуманного согласия/принудительного выхода. Техническое удаление архивного текста: body=NULL, deleted_at=now, сохранение метаданных/id/FK согласия; удалённый текст нигде не отображать. ACTIVE удалять нельзя. DRAFT и ARCHIVED удаляются только явно администратором; удалённое ID не переиспользовать.

## Публичный API

GET /public/rules -> `{active:null|Rule,versions:RuleSummary[]}`. RuleSummary `{id,version,title,status:'ACTIVE'|'ARCHIVED',created_at,published_at,archived_at}`, UTC ISO/null. Rule = summary + body string. versions: только опубликованные неудалённые ACTIVE/ARCHIVED, по version DESC; active — текущий полный текст или null.

GET /public/rules/:id -> Rule или404 RULES_NOT_FOUND; DRAFT/deleted недоступны. Публичные читатели не видят черновики, данные согласия или автора. Старые опубликованные версии доступны в том же окне через список архива.

## Административный API

GET /admin/rules -> `{active_version_id:UUID|null,versions:AdminRule[]}`, AdminRule=Rule плюс status DRAFT/ACTIVE/ARCHIVED; body string, список неудалённых версий DESC.

POST /admin/rules `{title:trim1..150,body:trim1..100000}` ->201 AdminRule DRAFT.

POST /admin/rules/:id/save `{title,body}` -> AdminRule; только DRAFT, иначе409 RULES_VERSION_LOCKED.

POST /admin/rules/:id/publish `{}` -> AdminRule ACTIVE; только DRAFT. Транзакция сериализует publish/save/delete (общий advisory lock), отправляет текущую ACTIVE в ARCHIVED с archived_at, выбранную DRAFT в ACTIVE с published_at. Повтор publish той же ACTIVE идемпотентен, архив не изменяется. ARCHIVED нельзя повторно активировать; создать копию новым черновиком. Не потерять старую версию при гонке публикаций.

POST /admin/rules/:id/delete `{}` -> `{status:'deleted'}`; только DRAFT/ARCHIVED, ACTIVE ->409 RULES_ACTIVE_DELETE_FORBIDDEN. После удаления404 для текста. Согласие пользователей не удаляется вместе с контентом, сохраняет version_id и timestamp.

Все admin маршруты защищены ролью; строгие тела и UUID, неверный формат422. API request helper уже поддерживает POST, методDELETE не добавлять.

## Согласие при регистрации

POST /auth/register добавляет обязательные `rules_accepted:true`, `rules_version_id:UUID` (к существующим display_name/tg_username). До записи pending под блокировкой проверяет текущую ACTIVE: нет ->409 RULES_UNAVAILABLE, отсутствует/false согласие ->422 VALIDATION_ERROR, другая версия ->409 RULES_CHANGED. В pending сохраняются точно просмотренное ID и время согласия (сервер). Правильный код/Telegram не заменяет галочку.

Создание нового users через оба пути (/auth/code/verify, /bot/verify) требует корректного сохранённого согласия на опубликованную неудалённую версию (ACTIVE либо ARCHIVED) и копирует ID/время в users. Если новая редакция опубликована после уже принятой pending, старое действительное согласие допускается до штатного15мин expiry — не заставлять повторять Telegram-код. Если принятую архивную редакцию явно удалили до завершения новой регистрации ->409 RULES_CHANGED. Повторный вход/регистрация существующего users не перезаписывает первоначальное согласие. /auth/login, бот выдачи кода и текущие сессии не требуют нового согласия; исторические pending без согласия не могут создавать новых пользователей.

GET user/profile и admin/users дополняются `accepted_rules_version_id:UUID|null`, `rules_accepted_at:ISO|null`; новые поля обязательны в ответе, не показывать фиктивное согласие у старых аккаунтов.

## UI

Ссылка «Правила» в гостевой шапке; чтение доступно также в меню участника/гостевого лидерборда. Открывает отдельное доступное модальное окно, прокрутка длинного текста и выбор действующей/архивной версии. Закрытие правил возвращает к форме регистрации без потери имени/username/галочки и без сброса auth/code90s. Модальное окно правил рендерить поверх текущего AuthModal, не заменять его state. Правила — текст, не HTML.

На начальном шаге регистрации показать незаполненный обязательный checkbox «Я ознакомился и согласен с правилами турнира», ссылка открывает текущую редакцию с её номером. Отправка блокируется без галочки/active/регокна. POST получает то ID, которое показывали при согласии. При RULES_CHANGED перезагрузить правила, снять галочку, показать новое содержание/запросить согласие; не перезапускать Telegram по причине обычного просмотра. При отсутствии active — «Правила ещё не опубликованы. Регистрация временно недоступна», вход существующих пользователей доступен.

Если RULES_CHANGED получен на подтверждении кода из-за удалённой принятой версии, вернуть пользователя к согласию/новым правилам без потери имени и Telegram. Создать новую pending после нового согласия, не запрашивать замену нерасходованного OTP автоматически: действующий код может завершить новую pending до своего срока. Таймер90сек и ручная повторная выдача сохраняются; просмотр правил сам по себе pending не сбрасывает.

В админке восьмой раздел «Правила»: список DRAFT/ACTIVE/ARCHIVED, редактор title/body, создать/сохранить черновик, просмотр/копирование архивной в новый черновик, кнопка публикации, явная подтверждаемая кнопка удаления неактивной версии. Активный/архивный текст не редактируется. Публикация явно сообщает об архивировании прежней версии. Поддержать вставку/загрузку .txt/.md содержимого в редактор без деплоя. Не создавать новые фиктивные призы, документы согласия или дополнительные бизнес-процессы.

## Проверки и импорт

PG временная БД: доступ, нетактивных правил, точное согласие/версия при регистрации в обоих путях, старые users и вход, гонки publish/архивирования, удалениеархива без потери FK согласия, неизменяемость активной/архивной редакции. Старые auth tests регистрировать с явно опубликованной fixture-версией и согласием, сохранить первоначальные gates. tablecount теперь9.

Browser fixture перед регистрацией публикует короткие тестовые правила. Новый сценарий: checkbox без default, просмотр/возврат не теряет форму, регистрация по коду сохраняет accepted version, админ публикация новой версии архивируетстарую, публичное чтение архива и удаление. Нельзя молча публиковать пользовательский исходный черновик ради тестирования. Реальные данные согласия не выдумывать.

Root импортирует приложенный текст как DRAFT в локальную БД после миграции008; повторный импорт того же title/body не должен создавать дубликаты. До публикации в админке новый signup недоступен, три существующих аккаунта могут входить.
