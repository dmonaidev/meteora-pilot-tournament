# Утверждённые решения и изменения контрактов

[1.3: название турнира](tournament-name-v1.3.md) добавляет отдельное редактируемое название, первоначально PILOT TOURNAMENT. Ввод расписания использует гарантированный24часовой формат и примечание UTC по уточнению1.1.

Текущее дополнение [1.2: квалификация Special Gift](partner-qualification-v1.2.md) вводит реферальный URL из админки, путь участника и короткий статус заявки. Вывод SOL — на **Ваш турнирный кошелёк**. Подтверждение условий партнёра выполняет администратор вручную.

Версия 0.2.1. Решения владельца продукта от 8 октября 2026 года включены в действующие сценарии, словарь, БД, API, интерфейсы и приёмку. Прежние вопросы Q-01–Q-05 закрыты этими решениями; младший разработчик не выбирает старые варианты.

## Основной результат и сортировка

Администратор загружает готовый pnl в tournament_scoring. PNL — абсолютный финансовый результат, не процент доходности. Приложение не рассчитывает его из капитала и не собирает финансовые данные самостоятельно. Сортировка публичного leaderboard: pnl DESC NULLS LAST, затем users.id ASC для стабильного порядка равных PNL. Дополнительный порядок не меняет финансовый результат и не задаёт отдельное правило выдачи призов.

roi_percentage — необязательный справочный процент, который администратор может загрузить. Он не вычисляется сайтом, не заменяет pnl, не влияет на сортировку и не участвует в разрешении равных PNL. initial_capital, current_capital и in_positions_amount сохраняются как необязательные справочные значения администратора.

## Кошелёк и подтверждение вывода

Пользователь вручную вводит wallet_address и withdrawal_tx_hash — хэш транзакции вывода с биржи на этот адрес. Данные сохраняются в одной wallets. Проверяется формат адреса и наличие текстового хэша; автоматическая проверка транзакции и криптографическое доказательство владения не выполняются.

Поданный адрес получает UNDER_REVIEW; администратор вручную устанавливает VALID или INVALID с rejection_reason. Signature не требуется и исключён из запросов и алгоритмов. Хэш показывается участнику в ЛК и администратору, не публикуется в leaderboard.

exchange_uid — UID аккаунта на бирже, строковое поле partner_rewards. Он не является users.id или UUID кошелька. В интерфейсе заполнения данных регистрации/ЛК расположить поля «Кошелёк Solana», «Хэш вывода с биржи на этот кошелёк» и существующий блок UID биржи. UID обязателен для PARTNER_GIFTS; withdrawal_tx_hash обязателен при подаче кошелька независимо от категории награды.

## Фиксация кошелька после старта

Начало единственного текущего турнира задаётся обязательной серверной настройкой TOURNAMENT_START_AT в UTC. При now >= TOURNAMENT_START_AT пользователь не может изменить существующий wallet_address независимо от регистрации, проверки кошелька или наличия scoring. Это правило проверяет сервер при записи, а интерфейс показывает wallet_address_locked.

Первая подача, если кошелька ещё нет, не является сменой и этим правилом не запрещается. Повторная подача того же адреса, исправление хэша и ручная проверка разрешены; новый хэш требует новой проверки. Ввод после старта не создаёт право на допуск сам по себе.

Исключение владельца: администратор может в отдельном случае связать прежний прогресс с новым кошельком. Это закрытая административная операция с сохранением того же users.id и строки tournament_scoring. Публичная кнопка смены, обещание такого исключения участнику и обычный пользовательский endpoint для обхода запрета не создаются. Порядок исключения описан в ALG-11.

## RFC-05 Изменение результата и данных допуска

Статус: принят оркестратором на основании указаний владельца. Воздействие: Agent.md; SC-05/06/10/11/12; ALG-05/08/09/11; словарь; БД; API; интерфейсы; приёмка.

Изменения:
- tournament_scoring.pnl: NUMERIC(20,6) NOT NULL, обязательный готовый результат администратора; отрицательные значения допустимы.
- roi_percentage: FLOAT NULL DEFAULT NULL, необязательный справочный результат администратора.
- initial_capital/current_capital/in_positions_amount: NUMERIC(20,6) NULL DEFAULT NULL, необязательные справочные поля.
- wallets.withdrawal_tx_hash: VARCHAR(255) NOT NULL для всех новых подач.
- signature исключён из рабочего контракта.
- profile.wallet_address_locked: вычисляемый boolean, не колонка БД.
- TOURNAMENT_START_AT: серверная конфигурация, не новая таблица.
- admin/wallets/validate сравнивает проверенные wallet_address и withdrawal_tx_hash с текущей записью.
- admin/scoring/import требует tg_id и pnl; отсутствующие справочные поля заменяет null.
- При повторном импорте строки справочные поля не наследуются молча от прежней загрузки.

Новые таблицы и автоматические источники не добавляются. Фильтр допуска и правило reward_tag сохраняются.

## Сохранённые правила

- Первая регистрация сверяет tg_id с initial_users: APPROVED_AUTO либо PENDING_VALIDATION.
- Ручное решение: APPROVED_MANUAL/REJECTED с обязательным admin_notes.
- Допуск leaderboard: одобренная регистрация и VALID кошелёк; UID влияет только на reward_tag.
- Любой регистрационный статус разрешает заполнить данные; после старта действует отдельное ограничение смены адреса.
- RESPECT → exchange_uid=null, uid_status=NOT_REQUIRED. Новый PARTNER_GIFTS/UID → UNDER_REVIEW.
- Нет scoring → допущенный участник остаётся в списке с null метриками после участников с PNL.
- Polling 3 секунды, жизнь pending session 15 минут.
- display_name 3–20 символов, существующее имя и ручной статус не затираются повторной регистрацией.
- initial_users импортируется по tg_id; импорт не меняет существующие users.

## Параметры развёртывания

Перед запуском задаются фактический TOURNAMENT_START_AT, имя бота, серверные секреты и список администраторов. Это значения конфигурации, а не незакрытые правила продукта. PNL и справочные суммы администратор подготавливает в единой принятой единице; приложение не конвертирует их.

## RFC-06 Согласование формулировок после одного прогона

Статус: принят оркестратором 8 октября 2026 года в рамках проверки согласованности. Версия спецификации 0.2.1. Новые функции и таблицы не вводятся.

Влияние: Agent.md, SC-01/03/07/09/12, ALG-07/08/10, API, приёмка и общая карта модели.

- Восстановление допуска показывает сохранённый scoring того же user_id и после разрешённой смены адреса; прежняя оговорка SC-12 удалена.
- RESPECT с пустой строкой UID получает 422, как следует из контракта «отсутствует либо null». Переход на RESPECT задаёт NOT_REQUIRED.
- Сводный сценарий Agent.md согласован с повторной регистрацией, случайным token и полным ответом с expires_at.
- Повтор bot/verify возвращает текущий registration_status, а не историческую копию.
- Счётчики импорта вычисляются внутри транзакции после блокировки. Для initial_users импорты сериализуются блокировкой существующей таблицы; для scoring используются предусмотренные блокировки users.
- Чтение профиля/админки согласовано с правилами согласованного чтения leaderboard.
- Имя rejection_reason в описании API приведено к фактическому JSON-ключу.

Проверка и ограничения результата зафиксированы в [отчёте](../review/consistency-pass.md).
