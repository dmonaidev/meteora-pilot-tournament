# Telegram-код для входа с другого устройства — дополнение 0.5

Принято оркестратором 8 октября 2026 года по поручению владельца. Дополняет 0.3 и 0.4. Админка 0.4 сохраняется. Работа локальная; серверный деплой не выполняется.

## Пользовательский сценарий

1. Пользователь указывает на сайте display_name при регистрации и Telegram username либо числовой Telegram ID. ID нужен аккаунтам без username; его бот показывает вместе с кодом.
2. Сайт создаёт обычную pending session через существующий register/login и показывает имя/адрес самого бота @lptournamentsupport_bot и поле «Код из Telegram».
3. Пользователь открывает бота на телефоне, отправляет /start без длинного параметра. Бот получает от защищённого backend одноразовый код из шести цифр и отправляет его в личный чат вместе с username/ID и сроком 5 минут.
4. На сайте пользователь вводит код. Сайт передаёт token своей pending session, telegram_identifier и code на новый endpoint. Сервер подтверждает Telegram-личность и выдаёт JWT. Администратор открывает админку, участник — ЛК.

В окне нет длинной команды для переписывания. Кнопка открытия бота ведёт на обычный адрес бота без start token. Username/ID идентифицирует адресата, но право входа доказывает одноразовый код, выданный в Telegram. После перезагрузки окна сохраняются mode/session/identifier, без сохранения самого кода. Уже существующий deep link и bot/verify поддерживаются для прежних ссылок.

## Новые API

POST /api/v1/bot/code: заголовок X-Bot-Secret, тело {tg_id:positive safe integer, tg_username:string|null}. Только доверенный бот с реальными message.from полями. Возвращает {code:string ровно 6 цифр, expires_at:ISO UTC, telegram_identifier:string}. Username возвращается с @; при отсутствии username возвращается десятичный tg_id. Гость/обычный JWT не заменяет секрет бота. Код не попадает в журналы, публичные API или админские ответы.

POST /api/v1/auth/code/verify: тело {token:reg_/auth_ website session token, telegram_identifier:string 1–255, code:string ровно 6 цифр}. identifier — username с/без @ либо положительный safe integer ID в десятичной форме. Ответ как подтверждённый auth/session: {is_used:true, access_token:string, token_type:'Bearer', registration_status:enum}. Неверный, истёкший, использованный код или исчерпанные попытки → 422 CODE_INVALID с нейтральным текстом «Код неверен или истёк. Отправьте /start боту для нового кода». TTL исходной website session остаётся 15 минут. Неизвестный пользователь при AUTHORIZATION → USER_NOT_REGISTERED; профиль без display_name не создаётся, правильный код не расходуется, чтобы можно было перейти к регистрации.

Если website session содержит expected_tg_username, username проверенного получателя должен совпасть с ним. При REGISTRATION повторно используются существующие users по tg_id без смены имени/ручного статуса. Новый участник использует initial_users и APPROVED_AUTO/PENDING_VALIDATION. Новый users и связывание website session + расходование кода фиксируются в одной транзакции. Событие registration только для фактического нового пользователя после COMMIT, по существующему контракту уведомлений.

## Хранение и ограничения

Новой таблицы нет. Миграция 003 добавляет в pending_sessions nullable otp_tg_id BIGINT, otp_tg_username VARCHAR(255), otp_code_hash CHAR(64), otp_attempts SMALLINT NOT NULL DEFAULT 0 с диапазоном 0–5. Грант имеет случайный внутренний token с префиксом otp_, session_type=AUTHORIZATION, display_name=null, tg_id=null, is_used=false. otp_tg_id не FK, потому что код должен выдаваться и до регистрации. Код хранится только как HMAC-SHA256 с серверным секретом и солью из внутреннего token, tg_id и code. Соль/token гранта не возвращаются клиенту.

Срок кода created_at+5 минут, сравнение по серверному времени. Не более пяти неверных проверок на последний грант; счётчик неверной попытки должен сохраняться даже при ответе об ошибке. Выдача нового кода инвалидирует прежний активный код того же Telegram ID. Генерация криптографическим randomInt с сохранением ведущих нулей. Выдача и проверка сериализованы по Telegram ID (pg_advisory_xact_lock BIGINT) с повторным чтением гранта под блокировкой. Две параллельные проверки не могут использовать один код дважды.

Успех делает грант is_used=true, tg_id=подтверждённый users.tg_id и otp_code_hash=null; соответствующий website token также связывается. Ошибка не создаёт пользователя или JWT. После успеха обычный website polling продолжает работать, пока действительна session. Коды проверяются только в рамках конкретного username/ID, а не глобальным поиском шести цифр. Нейтральные ошибки не раскрывают наличие пользователя. /auth/code/verify: максимум 10 запросов за минуту на IP до создания/изменения записей; /bot/code: максимум 60 за минуту, как bot/verify.

Административный sessions сохраняет поля 0.4. Гранты otp_ не раскрывают внутренний token, хэш, код или новые внутренние поля; expires_at/expired для гранта используют 5 минут, для website sessions 15 минут.

## Приёмка

- Реальный /start без параметра возвращает код на телефон и не требует браузера Telegram.
- Верный код + username/ID + website session завершает регистрацию и повторный вход; админская роль определяется только ADMIN_TG_IDS.
- Неверный код, другая личность, граница 5 минут, шестая попытка, повторное использование и прежний код после новой выдачи не дают JWT.
- Конкурентное использование одного кода даёт только один успешный вход.
- Username=null работает через Telegram ID; ведущие нули кода сохраняются.
- Никакие admin/public ответы не содержат код/хэш/внутренний token.
- Пять данных админки, поиск, пагинация и неизменность даты после старта продолжают работать.
