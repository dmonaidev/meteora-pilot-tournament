# Единая модель продукта

Версия 0.2.1.1. Собрана 8 октября 2026 года из действующих сценариев, словаря, БД, API и алгоритмов. Назначение: зарегистрировать участника, проверить его допуск и показать загруженный администратором PNL в лидерборде.

Это карта для совместного чтения спецификации. Точные форматы запросов находятся в [API](../contracts/api.md), ограничения хранения — в [БД](../contracts/database.md), порядок операций — в [алгоритмах](algorithms.md).

## 1. Компоненты и данные

Сайт и Telegram-бот обращаются к одному серверу приложения. Только сервер читает и меняет одну PostgreSQL. Отдельной синхронизации копий баз нет: после успешной записи интерфейсы читают актуальный ответ API.

| Таблица | Идентификатор / связь | Назначение и источник |
| --- | --- | --- |
| initial_users | tg_id — PK | Список автоматического допуска, импортирует администратор |
| users | id — UUID PK; tg_id — UNIQUE | Постоянный профиль; Telegram ID подтверждает бот |
| wallets | id — UUID PK; user_id — UNIQUE FK users.id | Одна текущая пара адрес/хэш и ручная проверка |
| partner_rewards | user_id — PK/FK users.id | Выбор награды, строковый UID биржи и его проверка |
| tournament_scoring | user_id — PK/FK users.id | Один текущий набор готовых метрик администратора |
| pending_sessions | token — PK; tg_id после подтверждения | Временная связь сайта с подтверждением Telegram |

initial_users.tg_id сопоставляется с users.tg_id при первой регистрации, но не является обязательным FK: пользователь может отсутствовать в исходном списке. pending_sessions.tg_id до подтверждения равен null. При подтверждении сессии профиль и связь с ним фиксируются в одной транзакции.

users.id связывает прогресс. wallet_address, withdrawal_tx_hash, exchange_uid и Telegram username не служат ключами связи scoring с участником. exchange_uid не является UUID.

## 2. Состояние участника

Модель состояния для чтения:

- R: users.registration_status — APPROVED_AUTO / APPROVED_MANUAL / PENDING_VALIDATION / REJECTED.
- W: отсутствие wallet либо UNDER_REVIEW / VALID / INVALID; вместе с адресом, хэшем и причиной отказа.
- G: отсутствие rewards; RESPECT + null UID + NOT_REQUIRED; либо PARTNER_GIFTS + непустой UID + UNDER_REVIEW / VALID / INVALID.
- S: отсутствие scoring либо обязательный pnl и четыре nullable справочные метрики.
- T: TOURNAMENT_START_AT; время проверяет сервер.

Это обозначения для документа, не новые поля API или БД.

| Вычисление | Правило | Где применяется |
| --- | --- | --- |
| Допуск в публичный список | R одобрен AND W=VALID | leaderboard |
| Видимость сохранённого scoring в ЛК | W=VALID AND S существует | profile.scoring; иначе null |
| Метка награды | PARTNER_GIFTS и UID VALID → Special Partner Gift; иначе RespectGift | leaderboard.reward_tag |
| Блокировка адреса | wallet существует AND now >= T | profile.wallet_address_locked и проверка записи |
| Срок pending session | now >= created_at + 900 секунд → истекла | bot/verify и polling |

Регистрация и кошелёк проверяются независимо. Даже при REJECTED пользователь с VALID wallet видит собственный загруженный scoring в ЛК, но отсутствует в публичном списке. UID не влияет на допуск. Отсутствие scoring не исключает допущенного участника: его публичные метрики равны null.

## 3. Сценарии → API → записи → чтение

Все пути имеют префикс /api/v1. Права и полные JSON-схемы — в API.

| Шаг | Запросы | Изменение | Последующий результат | Связь |
| --- | --- | --- | --- | --- |
| Регистрация / вход | POST /auth/register или /auth/login | Создание pending_sessions | token, bot_link, expires_at | SC-01–03; ALG-01 |
| Подтверждение Telegram | POST /bot/verify | Поиск/создание users, username, подтверждение session | success, текущий registration_status | ALG-02 |
| Завершение входа | GET /auth/session/{token} | Нет записей профиля | Ожидание либо JWT | ALG-03 |
| Допуск | POST /admin/users/moderate | Только статус users и admin_notes | APPROVED_MANUAL / REJECTED | SC-04; ALG-04 |
| Подача wallet/hash | POST /user/wallet | Оба значения атомарно в wallets | Статус пары; scoring сохранён | SC-05; ALG-05 |
| Проверка wallet/hash | POST /admin/wallets/validate | Только статус и причина wallets | VALID / INVALID текущей пары | SC-06; ALG-05 |
| Выбор награды | POST /user/rewards | partner_rewards | RESPECT либо проверка UID | SC-07; ALG-06 |
| Проверка UID | POST /admin/rewards/validate | Только uid_status | Изменяется reward_tag | SC-08; ALG-06 |
| Исходный список | POST /admin/initial-users/import | Upsert initial_users по tg_id | inserted/updated; users без изменений | SC-09; ALG-07 |
| Загрузка результата | POST /admin/scoring/import | tg_id → users.id → upsert scoring | Полный набор метрик заменён | SC-10; ALG-08 |
| ЛК / админка | GET /user/profile или /admin/users | Нет | Связанные данные; в админке scoring не скрывается | SC-11; ALG-10 |
| Публичный результат | GET /public/leaderboard | Нет | Фильтр допуска, метрики, метка, порядок | SC-12; ALG-09 |

Закрытое исключение ALG-11 выполняется доверенной административной операцией; обычного endpoint и кнопки для него нет.

## 4. Переходы и сохранение данных

### Регистрация

Новый tg_id: есть в initial_users → APPROVED_AUTO, иначе PENDING_VALIDATION. Повторная регистрация или вход сохраняют users.id, display_name, registration_status и admin_notes. Обновляется актуальный Telegram username. Ручная модерация с обязательным комментарием задаёт APPROVED_MANUAL либо REJECTED. Импорт списка не меняет ранее созданные профили.

### Кошелёк

| Действие | До T | В T и после T |
| --- | --- | --- |
| Первая подача адреса и хэша | UNDER_REVIEW | UNDER_REVIEW |
| Изменение существующего адреса | Та же запись, новая пара, UNDER_REVIEW | 409 WALLET_CHANGE_LOCKED; без записи |
| Новый хэш того же адреса | UNDER_REVIEW | UNDER_REVIEW |
| Та же пара VALID / UNDER_REVIEW | Сохранить статус | Сохранить статус |
| Та же пара INVALID | UNDER_REVIEW, очистить причину | UNDER_REVIEW, очистить причину |
| Админ проверяет текущую пару | VALID / INVALID | VALID / INVALID |

Проверяется формат адреса, обязательность текстового хэша; подпись не запрашивается. Администратор проверяет вывод с биржи на этот адрес вручную. Устаревшая пара в запросе администратора → WALLET_CHANGED. INVALID требует rejection_reason; VALID/UNDER_REVIEW имеют null.

Любая разрешённая правка кошелька сохраняет scoring. При закрытом исключении после старта также сохраняются users.id, wallets.id и все метрики; новая пара проходит UNDER_REVIEW → ручную проверку. Публичная видимость восстанавливается после выполнения обоих условий допуска.

### Награды

RESPECT принимает отсутствующий exchange_uid либо null; даже пустая строка в запросе отклоняется. В БД UID=null, статус NOT_REQUIRED. Новый PARTNER_GIFTS или изменённый UID → UNDER_REVIEW. Идентичная пара типа/UID сохраняет статус. Проверка UID не изменяет wallet/hash, регистрацию или scoring.

### Результат

PNL загружает администратор. Обязателен signed decimal string; ноль и отрицательные значения допустимы. Необязательные initial_capital, current_capital, in_positions_amount и roi_percentage отсутствуют → сохраняются как null, включая повторную загрузку поверх прежних значений. Расчёта метрик приложением нет.

Одна ошибочная строка, неизвестный tg_id или повтор tg_id внутри набора отменяют весь импорт. Пользователи вне набора не изменяются. Сортировка: точное числовое pnl DESC NULLS LAST, затем users.id ASC. ROI не используется даже для разрешения равенства.

## 5. Атомарность и обновление интерфейсов

- Верификация бота блокирует pending session; users.tg_id уникален. Профиль и подтверждение сессии фиксируются вместе.
- Операции кошелька и наград блокируют users перед чтением дочерней записи. Админ сравнивает проверенные значения под той же блокировкой.
- Проверка запрета смены адреса получает серверное время после блокировки; открытая до старта форма не обходит запрет.
- Импорт initial_users получает блокировку таблицы внутри транзакции перед подсчётом существующих строк. Импорт scoring блокирует users в стабильном порядке id, затем считает inserted/updated и пишет весь набор.
- Профиль, административный список и leaderboard читают связанные данные согласованно. Чтение не меняет БД.
- После успешного изменения ЛК перечитывает profile; административный экран перечитывает свой список. Лидерборд отражает изменения при следующем GET. Фоновая рассылка обновлений не требуется.
- При ошибке интерфейс не показывает неподтверждённую запись как сохранённую. При WALLET_CHANGED/UID_CHANGED администратор перечитывает объект и проверяет актуальные значения.

## 6. Конфигурация и приватность

T задаётся обязательным TOURNAMENT_START_AT в UTC (ISO 8601 с Z); неверное/отсутствующее значение останавливает запуск. BOT_USERNAME формирует ссылку; BOT_API_SECRET защищает bot/verify. JWT требует серверного ключа и AUTH_JWT_TTL_SECONDS. Минимальный источник административных прав — серверный ADMIN_TG_IDS по ALG-10. Фактические значения задаются при развёртывании и не добавляют таблицы.

Публичный ответ содержит только user_id, display_name, пять метрик и reward_tag. Telegram ID/username, UID биржи, хэш вывода, комментарии и token не публикуются. ЛК получает собственный wallet/hash; админка — данные для ручной проверки.
