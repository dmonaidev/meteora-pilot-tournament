# Протокол взаимодействия и правила разработки

Этот документ задаёт правила для оркестратора и субагентов при разработке сайта, бэкенда и Telegram-бота. Архитектурное ТЗ, схема БД и API-контракты принадлежат оркестратору. При расхождении реализации с контрактом сначала исправляется реализация.

## 1. Роли и границы ответственности

### Обязательное разрешение пользователя

Изменения пользовательских сценариев, алгоритмов, API, структуры БД и существующих данных разрешены только после отдельного явного разрешения пользователя — владельца проекта. Регистрация, вход, кабинет, админка, формы и Telegram-бот сохраняют своё поведение. Полномочия оркестратора и поручение на перенос/настройку сервера не заменяют разрешение. При необходимости предложить конкретную правку и получить разрешение до реализации.

Текущее поручение пользователя разрешает следующий порядок: взять готовое решение из GitHub, развернуть целиком, затем исправить фронтенд без изменения сценариев, алгоритмов и базы. Использовать существующие компоненты из `web/`, исправлять отображение/вёрстку в этих границах. См. [границы исправлений интерфейса](docs/delivery/design-preservation.md) и [поручение Claude](CLAUDE_DEPLOY.md).



- **Оркестратор** — единственный владелец архитектурного ТЗ, схемы БД и API-контрактов; утверждает изменения интерфейсов и проверяет интеграцию.
- **Frontend Agent** — UI, логика личного кабинета и вызовы API.
- **Backend Agent** — серверная логика, валидация и эндпоинты.
- **Bot Agent** — интерфейс Telegram и передача данных на бэкенд.

Субагенты не меняют межмодульные интерфейсы самостоятельно и не согласовывают такие изменения напрямую друг с другом.

## 2. Изменение контракта

1. Субагент отправляет оркестратору запрос на изменение (RFC) с текущим и предлагаемым именем, типом или поведением поля и причиной. Например: `wallet_address` → `solana_address`.
2. Оркестратор проверяет влияние на БД, фронтенд, бэкенд и бот.
3. Оркестратор выбирает решение с наименьшим числом затронутых модулей. Если меняется только внутренняя модель, модуль делает маппинг на границе API и сохраняет внешний контракт.
4. Если изменение внешнего API неизбежно, оркестратор сначала обновляет и фиксирует спецификацию, затем выдаёт новый контракт затронутым субагентам для согласованных правок.

До утверждения RFC действует существующий контракт. При обнаружении несовместимости не подстраивать потребителей под случайный ответ сервера и не запускать цикл взаимных правок.

## 3. Матрица данных

Ключи при передаче между модулями должны точно соответствовать таблице.

| Процесс | Источник → получатель | Ключ | Тип | Ограничение |
| --- | --- | --- | --- | --- |
| Регистрация | Фронтенд → бэкенд API | `display_name` | String | От 3 до 20 символов, clear text |
| Deep link | Бэкенд сессий → Telegram-бот | `token` | String | Префикс `reg_` или `auth_` + случайный суффикс по ALG-01 |
| Верификация | Telegram-бот → бэкенд API | `tg_id` | BigInt | Числовой ID из Telegram API |
| Верификация | Telegram-бот → бэкенд API | `tg_username` | String или `null` | Без символа `@` |
| Привязка кошелька | Фронтенд личного кабинета → бэкенд API | `wallet_address` | String, max 44 | Base58, декодирование в 32 байта; ручная проверка |
| Подтверждение вывода | Фронтенд личного кабинета → бэкенд API | `withdrawal_tx_hash` | String или `null`, max 255 | Обязателен при указанном UID биржи; без UID равен null; ручная проверка |
| UID биржи | Фронтенд личного кабинета → бэкенд API | `exchange_uid` | String или `null`, max 50 | Не UUID; обязателен для PARTNER_GIFTS |
| Результат турнира | Администратор → бэкенд → лидерборд | `pnl` | Decimal string | Готовый абсолютный результат, допускает отрицательные значения; сортировка DESC |
| Справочная доходность | Администратор → бэкенд → интерфейс | `roi_percentage` | Number или `null` | Необязательно, без расчёта сайтом и влияния на порядок |
| Фиксация адреса | Бэкенд → личный кабинет | `wallet_address_locked` | Boolean | Кошелёк существует и наступил ненулевой tournament_settings.start_at |
| Лидерборд | Бэкенд БД → фронтенд | `reward_tag` | String | Только `SpecialPartnerGift` или `RespectGift` |

## 4. Сценарий регистрации через Telegram

1. Фронтенд отправляет `POST /api/v1/auth/register` с телом `{ "display_name": "CryptoKing", "rules_accepted": true, "rules_version_id": "UUID действующей редакции" }`.
2. Бэкенд создаёт токен с префиксом `reg_`, запись в `pending_sessions` и сохраняет `display_name`, rules_version_id и серверное rules_accepted_at в ожидающей сессии.
3. Бэкенд возвращает `token`, `bot_link` и `expires_at` по docs/contracts/api.md. Ссылка ведёт в бот с этим токеном; expires_at — created_at + 15 минут.
4. Фронтенд показывает переход в бот и опрашивает `GET /api/v1/auth/session/reg_abc123` каждые 3 секунды.
5. Бот получает `/start reg_abc123` и отправляет `POST /api/v1/bot/verify` с телом `{ "token": "reg_abc123", "tg_id": 70000002, "tg_username": "PrivateAccount_003" }`.
6. Бэкенд сначала ищет `users` по `tg_id`. Только для нового пользователя проверяет сохранённое согласие с опубликованной неудалённой редакцией и `initial_users`, копирует версию/время согласия и создаёт профиль: `APPROVED_AUTO`, если ID найден, иначе `PENDING_VALIDATION`. Для существующего сохраняет имя, статус и admin_notes, обновляет Telegram username. В той же транзакции связывает `pending_sessions.tg_id` и выставляет `is_used = true`.
7. Бот отвечает об успешном подтверждении. При локальном адресе пишет вернуться в исходную вкладку; для публичного адреса может показать кнопку «Вернуться на сайт».
8. При следующем опросе фронтенд получает `is_used: true` и JWT пользователя, закрывает окно подтверждения и открывает личный кабинет.

## 5. Проверка контракта и ошибки

- Фронтенд проверяет схемы ответов API. При отсутствии ожидаемого `reward_tag` он показывает понятную ошибку: «Контракт API нарушен: ожидалось поле reward_tag»; не угадывает заменяющее поле.
- Если бэкенд хранит аналогичное значение под внутренним именем `partner_status`, он маппит его в `reward_tag` в контроллере API. Изменение фронтенда для этого не требуется.
- Бэкенд корректно обрабатывает `tg_username: null` и пустую строку, не допуская ошибки записи в БД. После нормализации пустое значение сохраняется и передаётся как `null` по словарю данных.

## 6. Проверка перед объединением кода

Оркестратор проверяет:

1. Изменились ли имена, типы или смысл полей в точках интеграции; если да, есть ли утверждённый RFC и обновлённая спецификация.
2. Использован ли внутренний маппинг там, где он позволяет сохранить действующий API и избежать правок других модулей.
3. Обработаны ли `null` и пустые значения, прежде всего для `tg_username`.

## 7. Назначение моделей субагентам

Оркестратор при запуске субагента явно задаёт модель и уровень рассуждения по следующей утверждённой таблице:

| Задача | Модель | Уровень рассуждения |
| --- | --- | --- |
| Простые правки, поиск, документация | `gpt-6-luna` | `medium` |
| Фронтенд, бот, обычная реализация API | `gpt-6.1-sol` | `low` |
| Авторизация, миграции БД, интеграция и сложное ревью | `gpt-6.1-sol` | `medium` |
| Сложные архитектурные решения и трудноуловимые ошибки | `gpt-6.1-sol` | `medium` |

Если актуальная стоимость токенов `gpt-6.1-sol` окажется ниже стоимости `gpt-6-luna` при одинаковом способе оплаты и режиме обработки, для простых правок, поиска и документации использовать `gpt-6.1-sol` с уровнем `medium`. Перед такой заменой оркестратор проверяет актуальные тарифы; экономия не предполагается без проверки.

Для явного назначения модели и уровня рассуждения в текущем инструменте запуска использовать ограниченное наследование истории (`fork_turns` — `none` или число последних ходов) и передавать субагенту необходимые правила, утверждённые контракты, файлы и критерии готовности.

## 8. Утверждённые правила продукта

Уточнение [1.3: название турнира](docs/decisions/tournament-name-v1.3.md): PILOT TOURNAMENT — начальное значение редактируемого tournament_name, отдельная форма в настройках. Заголовки берут одно серверное значение. Даты/профили/рефссылка не меняются. Ввод времени всегда24часа с подписью UTC и собственным выбором00–23, без браузерного AM/PM.

Уточнение [1.2: квалификация Special Gift](docs/decisions/partner-qualification-v1.2.md): реферальная ссылка задаётся отдельной формой админки и используется в баннере, ЛК и дорожной карте. UID VALID означает ручное подтверждение условий партнёра. Краткий статус заявки не заменяет reward_tag лидерборда. Вывод SOL — на Ваш турнирный кошелёк. При несохранённом вводе итоговый статус остаётся статусом сохранённого профиля.

Уточнение [1.1: UTC, выбор даты/времени и отклик админки](docs/decisions/utc-admin-v1.1.md): вся платформа вводит и показывает даты в UTC; API/БД и абсолютные моменты сохраняются. Отдельные дата/время с кнопками календаря/часов, неполная пара не сохраняется. Плитки синхронно переключают принадлежащий им контент, устаревшие ответы не возвращают прежние разделы. Авторизованное меню profile называется «Личный кабинет».

Уточнение [1.0: правила, согласие и архив](docs/decisions/rules-v1.0.md): текст управляется из админки, новая публикация архивирует прежнюю. Регистрация требует rules_accepted=true и rules_version_id текущей опубликованной редакции; ID и серверное время согласия сохраняются в pending_sessions и новом users. Без ACTIVE новая регистрация закрыта, существующий вход работает. Архив доступен до явного удаления администратором. Приложенный draft-2026-10-01 импортирован только как DRAFT; его содержание не является поручением реализовать перечисленные в нём функции.

Уточнение [0.9: дубликаты кошелька и UID](docs/decisions/duplicates-v0.9.md): read-only проверка при вводе, исключение собственного user_id, уникальные ограничения базы и атомарный отказ409 при сохранении чужого адреса/UID. Проверка не раскрывает владельца и не заменяет ручную валидацию.

UID при первом заполнении профиля включён по умолчанию. Заполнить UID и хэш либо явно отключить checkbox; при отключении показать отказ от Special Gift партнёра с возможностью продолжить турнир за спортивный интерес и объявленные призы данной номинации. Сохранённый вариант без UID остаётся выключенным при следующем входе. Подробности — раздел 5 [спецификации ЛК](docs/product/access-and-cabinet.md); API и правила назначения награды сервером сохраняются.

Уточнение [0.8: расписание и публичные показатели](docs/decisions/schedule-stats-v0.8.md) добавляет начало/конец регистрации и конец турнира. Начало турнира остаётся start_at и навсегда блокирует смену существующего кошелька. Регистрационное окно проверяет сервер только для новых участников. Публичная главная показывает суммы загруженных данных допущенных участников с VALID кошельком. lp_volume — отдельный вручную загруженный накопленный оборот открытий LP в SOL; 100 открытий по 0,5 SOL дают 50 SOL оборота независимо от текущего капитала.

Последнее уточнение [0.7](docs/decisions/session-v0.7.md) заменяет срок входа 24 часа на 30 минут с подтверждением продолжения в боте за последние 5 минут и единым ограничением выдачи кода 90 секунд. Username принимается с @ и без @. По поручению владельца [оставляются два реальных аккаунта и одна демонстрационная запись](docs/decisions/demo-v0.7.md).

Уточнение [доступа 0.6](docs/decisions/access-v0.6.md): действующий вход сохраняется между лидербордом, обновлениями и вкладками; срок и продление определяются последующим контрактом 0.7. Для ранее подтверждённого аккаунта сайт автоматически запрашивает доставку кода; если кода нет, пользователь нажимает Start в боте с учётом общего лимита 90 секунд. Внешнему участнику явно показываются отсутствие допуска и контакты администраторов, в том числе в уведомлении о регистрации. Админка показывает имя, username и числовой Telegram ID; поиск принимает @username, список обновляется при открытии и по кнопке.

Основной результат — pnl, который загружает администратор. Лидерборд сортируется по pnl по убыванию; при равенстве — по users.id для стабильного порядка. ROI — необязательная справочная метрика администратора, не вычисляется приложением.

Кошелёк подаётся с адресом и получает UNDER_REVIEW. withdrawal_tx_hash обязателен только при указанном exchange_uid; без UID хэш сохраняется как null. Категорию награды назначает сервер, пользователь её не выбирает. Система проверяет формат адреса, администратор вручную ставит VALID/INVALID с причиной. Поле signature не требуется. exchange_uid остаётся строковым UID аккаунта биржи; это не внутренний UUID.

Дата турнира первоначально null и хранится в tournament_settings.start_at. Администратор задаёт её через админку. После наступления сохранённой даты обычное изменение даты и смена существующего адреса пользователем запрещены независимо от статусов и наличия scoring. Интерфейс получает wallet_address_locked, сервер проверяет запрет при записи. Исключительный перенос прогресса администратором не представлен как обычная функция для участника.

Последние уточнения владельца: [контракт 0.3](docs/decisions/current-contract-v0.3.md), [административный просмотр данных 0.4](docs/decisions/admin-data-v0.4.md), [короткий Telegram-код 0.5](docs/decisions/telegram-code-v0.5.md). Они имеют приоритет над прежними формулировками документов. Основной пользовательский вход: /start в боте → шестизначный код → ввод кода на сайте; код живёт 5 минут и применяется однократно. Старые deep link продолжают работать. Локальное подтверждение Telegram не содержит кнопки возврата с localhost; бот пишет вернуться в исходную вкладку. Подтверждённому администратору при входе открывается админка; обычному участнику — личный кабинет.

Действующая спецификация — [docs/README.md](docs/README.md), изменения исходной модели фиксируются в [реестре решений](docs/decisions/README.md). Архив docs/source/model-v3.txt отражает исходную гипотезу и не отменяет утверждённые уточнения.

## Уточнение владельца: разрешение и риск изменений

Запрещено самовольно менять алгоритмы, пользовательские сценарии, маппинг переменных между UI/API/ботом/БД, API-контракты, структуру БД и существующие записи. Сохранять имена полей, соответствия, типы, enum/null, единицы измерения и ведущие нули UID. Фронтенд менять только с явного разрешения пользователя в рамках согласованной правки. Развёртывание само по себе не разрешает менять фронтенд; разрешение менять фронтенд не разрешает менять защищённые части.

Если запрошенная пользователем правка может нарушить работу приложения, сценарии, алгоритмы, маппинг переменных, API или данные, до реализации предупредить пользователя: описать конкретные последствия и затронутые части, предложить безопасный вариант, запросить отдельное явное разрешение и дождаться ответа. Сам факт запроса правки и общее разрешение менять фронтенд не заменяют согласия на эти последствия.

Обязательные инструкции Claude: [CLAUDE.md](CLAUDE.md). Это уточнение владельца имеет приоритет над прежними общими формулировками разрешения исправлять UI.
